# 实验日志

## 2026-11-16 会话 View 的 invocation 全量扫描

**假设**：`GET /api/conversations/{id}` 的 1.2s 中，`taskRuntimeTaskCost` 与 `ConversationMasterUsage`
对 50,065 条 invocation 的 JSON 解析/扫描占大头；把这两个派生值做成持久化合计，只读一行。
**代理计数**：每次 View 读取的 invocation 行数。旧：50,065；目标：0。
**做法**：新增 `task_invocation_totals` 表；`ensureTaskInvocationTotals` 冷启动时扫描一次并落库，
`RecordInvocationUsage` 后续按旧值增量更新；`taskRuntimeTaskCost`/`ConversationMasterUsage` 只读合计。
**护栏**：`TestInvocationTotalsFollowSettledWrites`、`TestTaskCostUsesThePersistedTotalsInsteadOfRescanningInvocations`
与既有 `TestContextTokensReadTheEstimate…`、`TestCacheHitRateDescribesTheSameRequest…` 全绿；全部 backend/app 测试通过。

**配对 A/B**（同一份 DB 副本，交替 10 次，p75）：
- 旧算法（读 50,065 行 + JSON 解码 usage/cost）：171.2ms
- 新算法（读一行合计）：2.06ms
- 代理指标与真实 View 同向：端点 p75 从 1.762s 降到 0.166s。

**走错的两步（已回退）**：
1. 用 SQLite `json_extract` 做 SUM/GROUP BY：1.25s，比旧算法更慢（modernc sqlite 的 JSON1 每行开销大）。
2. Go 里只取 cost 字符串再 typed decode：仍然要驱动扫 50,065 行，1.4s；瓶颈是驱动逐行 Scan，不是解码。

## 2026-11-16 编队快照缓存

**假设**：编队页每 3 秒刷新会重算 `fleetProjection`，其中 `loadFleetLedger` 对 5 万条 invocation 做
JSON 聚合，既拖慢接口也持续吃 CPU。编队数据只随事件变化，可用 `events.Max(cursor)` 等四个计数做快照键。
**做法**：`fleetSignature` 取 events/messages/invocations/tasks/artifacts 的最大/计数；
`fleetPayloadCached` 命中返回上一份字节，签名变化才重算。
**验证**：`TestFleetSignatureFollowsTheEventsItDependsOn` 断言新事件让签名变化。
**结果**：编队页重复刷新走缓存；接口首次仍按 2s 量级（下次用合计表继续降）。

## 2026-11-16 启动关键路径：先让 Main 可用，再加载白板

**观测**：启动后 App 同时发起 `/api/conversations`、`/api/conversations/{main}`、`/api/fleet`、
`/api/insights`、`/api/trajectory`；四路重活互相争抢，Main 请求从 60ms 被拖到 4–18s。
**做法**：`openNative` 里把白板数据加载闸门关到 `state.load()` 返回之后；之前任何
`ensureUsage/ensureFleet/ensureTrajectory/ensureInsights/...` 只记 pending 不发请求；
Main 就绪后开闸、再触发白板加载。
**验证**：`TestBoardDataWaitsUntilTheMainConversationIsReady`：闸门关闭时三个 ensure 都不发请求，
开闸后才请求 `/api/insights`。
**证据**（临时 HTTP trace，同一 daemon）：
- 闸门前：`/api/conversations` 714ms + Main 3.98s ≈ 4.7s 才可用；另一轮被拖到 18s。
- 闸门后：`/api/conversations` 758ms + Main 633ms ≈ 1.39s 可用；白板请求此时才开始，不挡 Main。

## 2026-11-16 轨迹快照复用

**观测**：`/api/conversations/{id}/trajectory` 每次重新扫 20k 消息、50k invocation、工具调用，
冷缓存 5.8s，并发时 15s，并拖慢 Main 的 3 秒刷新。
**做法**：`trajectories` 表加 `signature` 列（migration v62，幂等）；保存时记录依赖签名
（messages/invocations/tool_calls/events/node_entries/nodes/instances/artifacts/agents 的 latest rowid），
读取时签名一致直接返回已存 payload，变化才重建并回写。
**验证**：`TestConversationTrajectoryServesTheStoredSnapshotUntilHistoryChanges`：
未变化时返回手写快照；追加一条消息后重新构建。
**结果**：真机 `GET trajectory` 27–72ms（之前 4–15s）；表内 Main 轨迹 payload 22.9MB。

## 2026-11-16 启动第一段：launchd 的 10 秒节流

**观测**：临时给 App 加启动阶段 trace，`launchAgentBoot` 恰好 10.0s；再拆 `launchctl` 三步：
bootout 10ms、bootstrap 8ms、`kickstart -k` **10.0s**。plist 是 `RunAtLoad=true`，bootstrap 已经拉起 daemon，
紧接着的 `kickstart -k` 又把它杀掉，launchd 对 10 秒内反复拉起的 job 做节流，整段卡在 kickstart。
**做法**：启动与重启计划都只做 `bootout + bootstrap`，不再 `kickstart -k`；RunAtLoad 负责拉起。
**验证**：`TestLaunchAgentReloadsTheJobWithoutKickstartingItAgain`、`TestLaunchAgentStartUsesRunAtLoadInsteadOfKickstartingAgain`。
**证据**（open → console.json）：
- 改前：18.59s（app 0.09s / daemon 进程 11s / console 再 8s）
- 改后 3 次：5.00s、6.96s、11.87s（中位约 6.9s；app 进程到 daemon 进程 1s，daemon 初始化 4–10s）。

## 2026-11-16 启动索引：active 查询不再全表扫

**观测**：daemon 初始化剖面里 `RebuildExecutionSlots` ~1.9s、`dispatchQueuedMasterMessages` ~1.25s。
在 DB 副本上直接量：
- `SELECT id FROM operations WHERE instance_id IS NOT NULL AND (state='intent' OR (worker_active=1 AND waiting_slot=0))` 2.48s，计划 `SCAN operations`。
- 待发消息查询 1.06s，计划从 conversations 索引进、但在 messages 上按 conversation 走。
**做法**：migration v63 建三个 partial index：
`operations_intent(state) WHERE state='intent'`、`operations_worker(worker_active,waiting_slot) WHERE worker_active=1`、
`messages_queue(state) WHERE state IN ('pending','queued')`。
**验证**：`TestStartupRecoveryQueriesUseTheirIndexes` 断言 slot 查询走 `MULTI-INDEX OR` 两个索引、消息查询走 `messages_queue`。
**结果**：副本上 slot 查询 2.48s→0.00s，消息查询 1.06s→0.00s；建索引一次性约 4.4s（DB 副本）。
真机 open→console：3.47s / 1.23s（round 3 为 5.00/6.96/11.87s）；daemon 初始化 3.21s / 1.48s（之前 5–8s）。

## 2026-11-16 空闲时不再 40ms 扫一次待发工作

**观测**：App 退出后 daemon 仍占 ~19.5% CPU。`GraphHost.drive` 在 execute 模式每 40ms 调一次
`Execution.Pump()`，每次都要 `pumpGraphs()`（查 DB）和 `readyNodes()`（查 DB），空闲时也照跑。
**做法**：Pump 返回 `ExecutionDispatch`；drive 用 `dispatched` 决定下一拍间隔：
有派发 20ms，无派发 200ms；`graphDriveDelay` 独立成纯函数便于断言。
**验证**：`TestTheGraphHostPollsFastOnlyWhileWorkIsDispatched` 断言空闲 200ms、有活 20ms。
**结果**：daemon 瞬时 CPU（App 退出后）19.5% → **7.9%**；App 运行时 20.2% → **12.1%**。

## 2026-11-16 轨迹 payload 只带 UI 实际显示的窗口

**观测**：Main 轨迹 payload 22.9MB：turns 13.9MB（837 轮）、requests 9.0MB（50,065 次），
但 UI 只渲染最后 20 轮、最后 60 次趋势、8 条请求列表和最近一次请求详情。
**做法**：服务端保存/返回前裁剪到 turns=20、requests=60，新增 `requestOffset` 记住被裁掉的前缀；
App 用 offset 还原「第 N 次 / 共 N 次」。缓存签名加 `v2` 前缀让旧 22.9MB 快照失效重建。
**验证**：`TestTrajectoryPayloadKeepsOnlyTheDisplayWindow` 断言长度/offset/首条序号；
`TestTrajectoryRequestTotalIncludesTheSkippedPrefix` 断言 App 头部的总数。
**结果**：payload 22.9MB → **334,686B**（约 68×）；首次重建 5.5s，命中后 1.8–2.5ms；
轨迹页仍显示 837 轮、50,065 次请求，最近 60 次趋势。

## 2026-11-16 3 秒刷新先问版本，不再每次拉 1MB 会话

**观测**：`GET /api/conversations/{main}` 每次 1,033,894B / 0.35s，App 每 3 秒拉一次并解析、比对；
会话没变时这些字节和解析全是白做；artifacts 也每 3 秒再拉 41KB。
**做法**：
- 服务端新增 `GET /api/conversations/{id}/version`（约 95B）：签名含 conversation 元数据、
  events.MAC(cursor)、messages MAX(seq)/MAX(updated_at)、conversation_streams MAX(updated_at)、
  invocations MAX(rowid)、artifacts MAX(rowid)、tasks count、questions count；完整 View 也带 `version`。
- App 的 `conversationChatSource.Refresh` 先取 version；与上次相同直接返回 false，不拉完整会话；
  变化才拉完整并把新 version 记下。artifacts 只在会话变化或尚未加载时刷新。
**验证**：
- `TestConversationVersionFollowsItsTranscript`：追加消息后版本变化。
- `TestChatRefreshAsksForTheVersionBeforeTheWholeTranscript`：版本不变只请求 version；
  版本变化才再次拉完整会话。
**结果**：version 95–111B；首版全局签名要 96–228ms，改成按 conversation 取 messages/streams
并加 `messages_conversation_updated` 索引（migration v64）后 **0.65–1.3ms**。
App 运行且空闲时 daemon 瞬时 CPU 约 **7.4–10.4%**（pump 退避后为 12.1%，初始 20.2%）。
