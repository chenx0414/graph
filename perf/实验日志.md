# 实验记录

## 1. 构建时 gzip + HTTP 内容协商

假设：限速首屏约 3 秒主要来自 1.26MB 未压缩主脚本；预压缩减少网络字节，不改变解压后的内容，不增加请求时压缩成本。

实现：构建输出 JS/CSS/JSON 的 `.gz` 旁路文件，HTTP 按 Accept-Encoding 选择，保留原文件回退、Vary、逐请求读取和构建更新语义。不压缩 SSE、API、图片，不新增依赖。

第一版在 generateBundle 压缩，逐字节真实 HTTP 护栏发现 CSS 比最终文件少 12 字节（Vite 最后追加元数据），拒收。移至 writeBundle 压缩最终落盘文件后，全部资源和 5 种内容协商输入通过。

[paired.json](bench/paired.json)：Fast 4G 首屏 p75 2999→1035ms（-65.5%）。会话 176→179ms，Graph 111→110ms，均无提速结论。

[local.json](bench/local.json)：本地首屏 84.5→85.5ms，无收益；因此继续实验，不把网络档成绩冒充桌面成绩。

## 2. 设置、能力库、用量、工具统计按页面加载

假设：这些低频页面不应参与聊天首屏解析；保留聊天和 Graph 在初始路径，避免第一次打开 Graph 产生新的下载瀑布。

使用 React.lazy 和局部 Suspense，不改变 Activity 标签状态管理，不添加预取计时器。原有页面视觉/功能由真实界面回归验证。

[lazy-local.json](bench/lazy-local.json)：相对仅 gzip 版本，本地首屏 p75 91→79.7ms（-12.4%）。会话 86.5→86.6ms，Graph 68.2→67.5ms。网络首屏 JS 总传输从约 407KB 再降至约 368KB；此计数是解释变量，尚未以两次独立代码拆分证明为可通用的代理门禁。

最终结论使用相对最初基线的新一轮配对，不混合分时实验数据。没有单独提交：用户工作区已有大量未提交修改，本轮仅留下明确文件差异，不将其他工作混入提交。

## 全量护栏修复

第一次完整检查：262 文件通过，2 文件中的 4 条聊天 E2E 超时。全部经过测试延迟代理。最小真实 HTTP/Chromium 复现表明：代理用 Node fetch 读取 gzip 资源后正文已解压，但原样转发 Content-Encoding/Content-Length，浏览器因重复解码无法加载。仅移除这两个已失效的头，同一实际脚本恢复加载。修复两处 E2E 的传输代理，不减少业务断言、不改变时序控制、没有改用低层测试。

性能门禁反向校验：原始基线在首屏 p75 3008ms 处被拒绝；最终版本在收紧后的 Fast4G 1100/210/130ms、本地 100/105/85ms 三项上限下通过。
