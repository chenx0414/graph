# 报告：Main 会话打开/刷新提速

## 结论

Main 会话 `GET /api/conversations/{id}` 的 p75 从 **1.762s → 0.166s**（−90.6%），
p50 从 **1.209s → 0.066s**（−94.5%）。这条接口既是 App 启动后 Main 可用的阻塞调用，
也是运行中每 3 秒刷新调用的同一条路径。

## 前后对比（同一口径，同机，10 次 p75）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| `/api/conversations/{main}` p50 | 1.209s | 0.066s |
| `/api/conversations/{main}` p75 | 1.762s | 0.166s |
| 一次 View 读取的 invocation 行数 | 50,065 | 0 |
| 缓存命中后 task cost 读取 | ~1,060ms | 2–3ms |

配对 A/B 在 DB 副本上交替 10 次：旧算法 p75 171.2ms，新算法 2.06ms（83×）。

## 做法

- `task_invocation_totals` 持久化每个 task 的 cost 合计、usage 合计、最近 completion 与吞吐事实。
- 第一次读（升级后）扫描一次旧 invocations 并写合计；之后只读合计。
- `RecordInvocationUsage` 用旧行减、新行加做增量；`OpenInvocation` 在合计已存在时把新 invocation 计入
  未结算（unknown cost）与请求数。
- `ConversationMasterUsage` 按 task 合计机电（master task 数很少），不再逐条解析。

## 正确性

- 既有成本/上下文/缓存命中测试保持通过。
- 新增 totals 增量、重复结算、缓存命中测试。
- 真机返回：cost USD 187.019985896、cacheHitRateTotal 98.4%、contextTokens 17283，
  与优化前口径一致。

## 回滚

回滚本 commit 即回到逐条扫描；持久化表为新增表，可保留不影响旧代码。

## 第二轮：启动关键路径与轨迹快照

- 启动闸门：Main 请求在 0.61–0.76s 内完成，白板（fleet/insights/trajectory）等 Main 就绪后才发；
  同一 trace 口径下 Main 可用从 4.7s（另一轮 18s）降到 1.39s。
- 轨迹快照：`/trajectory` 由每次重建改为读签名匹配的已存 payload，真机 27–72ms（之前 4–15s）。
- 剩余瓶颈：daemon 从进程启动到写 `console.json` 约 15s，是下一轮头号目标；
  轨迹 payload 22.9MB，App 解析仍占内存/CPU。

## 第三轮：launchd 10 秒节流

启动 trace 证明 `launchAgentBoot` 的 10.0s 全部花在 `kickstart -k`：`bootstrap` 已按 RunAtLoad 拉起
daemon，紧接着又被 `-k` 杀掉，launchd 对 10 秒内重复拉起做节流。改成只 `bootout + bootstrap` 后：

| 口径 | 改前 | 改后 |
|---|---|---|
| open → console.json | 18.59s | 5.00 / 6.96 / 11.87s（中位 ~6.9s） |
| app 进程 → daemon 进程 | 11s | 1s |

剩余：daemon 初始化 4–10s，剖面指向 `RebuildExecutionSlots`、retention `sweepState`、
`dispatchQueuedMasterMessages` 等全库扫描；下一轮按索引/延后维护处理。

## 第四轮：启动查询索引

`RebuildExecutionSlots` 与待发消息恢复在 operations/messages 上全表扫（副本实测 2.48s、1.06s）。
migration v63 加三个 partial index 后两查询都走索引，真机 open→console 降到 **1.23–3.47s**，
daemon 初始化 **1.48–3.21s**（round 3 为 5–11.9s）。索引创建是一次性迁移，副本约 4.4s。

## 第五轮：空闲泵退避

daemon 的 `GraphHost.drive` 原来在 execute 模式每 40ms 泵一次（每次查 DB），空闲也照跑。
改为按上一拍是否派发工作决定间隔：有活 20ms、无活 200ms。daemon 瞬时 CPU 19.5% → **7.9%**（App 退出后），
App 运行时 20.2% → **12.1%**。

## 第六轮：轨迹 payload 裁剪

Main 轨迹原来 22.9MB（turns 13.9MB + requests 9.0MB），但 UI 只用最后 20 轮/60 次请求。
服务端裁到 20 轮 + 60 次并返回 `requestOffset`，App 用 offset 还原绝对序号；缓存签名加 v2 让旧快照失效。
payload **22.9MB → 334,686B（约 68×）**，命中后 1.8–2.5ms；轨迹页仍显示 837 轮、50,065 次请求。

## 第七轮：3 秒刷新先问版本

会话刷新原来每 3 秒拉 1,033,894B 并解析；新增 95B 的 `/version` 端点（events/messages/streams/
invocations/artifacts/tasks/questions 签名），App 版本未变时跳过完整会话与 artifacts。
版本变化时仍走完整 View。version 95–111B；初版全局签名 96–228ms，加
`messages_conversation_updated` 索引（migration v64）后 **0.65–1.3ms**；App 空闲时 daemon 瞬时 CPU 12.1% → **7.4–10.4%**。

## 第八轮：增量刷新

版本变化时不再拉全量消息：App 请求 `?after=<最新seq>&questions=open`，只合并新消息；
服务端默认返回全部问题，`questions=open` 时只返回 open 问题。
真机完整响应 1,033,994B → 934,370B；增量响应 **54,267B / 30ms**（约 19× 小于原完整拉取）。

## 第九轮：lean 刷新

增量响应里 continuations 占 49KB，而 App 不解析它。View 增加 `lean=1` 跳过该字段，
App 的 Load/Refresh 都带 `questions=open&lean=1`。增量响应 **54,267B → 5,278B（24ms）**；
完整响应 934,370B → 885,381B。默认响应不变。

## 第十轮：首屏只读 60 条

首次会话 885KB，但首屏只需最近几十条；Load 改为 `limit=60`（连同 questions=open&lean=1），
滚动到顶仍按 200 条分页。首次响应 **885,381B → 105,107B（8.4×）**，48ms；真机滚动验证更早消息可加载。

## 第十一轮：retention 移出启动路径

retention（`sweepState`）冷启动 1.41s，移入 `GraphHost.drive` 维护循环后异步执行。
taskRuntime 冷 4.01s→**2.58s**、热 0.57s→**0.44s**；open→console 冷约 4.2s→**2.7s**。
测试 `TestTheMaintenanceLoopAppliesRetention` 断言保留策略仍生效。

## 第十二轮：空闲泵 500ms

空闲泵间隔 200ms→500ms（有活仍 20ms），daemon 瞬时 CPU 8.3–9.7% → **5.6–5.7%**。
`Kick()` 仍会立即拉起 Drive，用户操作不受等待。

## 第十三轮：内核恢复快路径

无中断时不再开恢复事务：先查 running execution / active module op / inflight provider call，
全无直接返回；并给 `kernel_provider_calls(state)` 建索引。DB 副本上
`RecoverKernelExecutions` 616ms → **0.2ms**；真机 open→console 热 0.81s、冷 3.76s。

## 附表：编队页快照

`/api/fleet` 首次仍是 2s 量级，但按事件游标缓存后，App 每 3 秒的编队刷新命中缓存，
不再每次重算 5 万条 invocation 的 JSON 聚合。下一步改为读合计表，进一步降首次。

## 下一步（本轮未做）

`/api/fleet` p50/p75 仍约 2.3s/3.6s，`loadFleetLedger` 对 invocations/kernel_provider_calls
做 JSON 聚合，且编队页每 3 秒刷新时会持续吃 CPU；下一轮用同一合计表或按节点合计继续压。
