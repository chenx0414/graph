## 3. 阻塞：73 个测试文件

### 3.1 分类（实测，非估计）

| 类别 | 数量 | 含义 |
| --- | --- | --- |
| **A 类｜v2 缺能力** | **36** | 断言的是旧内核**独有能力** |
| **B 类｜迁移未完成** | **37** | v2 有能力，只是 setup/形状没对上 |

分类方法：特征匹配 + 与**实际失败集**求交，两类之和恰好等于 73，无落网。

A 类的能力缺口分布（旧 activation/evidence 20、verifier 闸门 12、返工环 11、
嵌套容器 8、旧 revision 8、合并冲突裁决 2、旧 templates/layout 2）。

**但这个分布后来被证明偏大**：`routes`/`when`/`optional`/`deliverable` 都能落到
**已实现**的 v2 能力上（见 §5），**真正需要产品决定的可能只剩 2 项**。

### 3.2 两类都**没有单一主因**
- B 类最高频签名只占 8 次，其余 4–6 次；
- A 类是七个不同能力。

**因此「找一个根因一次修好」的期待在这两类上都不成立。**
本会话后半段有**三次**「修的是真的、但不是瓶颈」，根因都是**没先做 A/B 分离**。

## 4. 迁移工具与其自身缺陷

工具：**`scripts/lift-v2-test-proposals.py`**（`60934cb`，**有测试**：`tests/m8/lift-tool.test.ts`）。

它处理三种调用形态，**每一种都曾经漏过**：

```ts
propose({ ...nodes }, 'id')    内联对象字面量
propose(spec, 'id')            变量
propose(graph({ ... }), 'id')  工厂调用   ← 最初缺失
```

**关键教训**：第三种形态最初没被处理，受影响文件**不是没迁移，而是以「旧形状」失败，
文件里看不出有什么不对**。

> **测量工具本身要被测试，否则它的缺口会被误读成产品规格问题。**
> 本会话在这上面栽了三次。

所有重写都用**真实括号配对**定位（字符串/模板/两种注释都会跳过），
不使用正则匹配括号——早期一次正则批量改写 56 个文件全部 parse error。

## 5. 提升器的字段丢失（已量化、已部分解决）

`input` 曾被**静默丢弃**大半个迁移期，唯一的症状是「适配器悄悄什么都没做」。

现在工具会报告丢了什么。**在 76 个真实文件上的实测**：

```
input 7   context 5   container 5   routes 2   optional 2   deliverable 2
when 3    verifier 1
```

| 字段 | 状态 |
| --- | --- |
| `input` | ✅ 往返**已验证**（`4d02f7e`，G1–G3） |
| `context` | ✅ 往返**已验证**（`4d02f7e`，G1–G3） |
| `routes` / `when` | ✅ 已映射为 **v2 router module**（`59d7b13`，§13.4 已实现） |
| `container` | ⚠️ **跨容器边不再被编造**（`6f9c4a1`）；**子图映射待做** |
| `verifier` / 合并冲突裁决 | ⏸ **待产品决定** |

**两种失败模式都要能报告**：
- **丢失**：字段无声消失 —— 与「本来就不重要」无法区分；
- **编造**：跨容器边被画成扁平边 —— 看起来像正常图，**比明显失败更糟**。

## 6. 需要用户决定的两项（§15.9）

### 6.1 `verifier` 多视角闸门
旧执行器有「一次交付要过多个视角的闸门」，v2 无对应物。
**§14 要求的是 acceptance + 证据**，闸门是否仍需保留？

- 保留 → 需在 v2 实现多视角验证；
- 丢弃 → 相关测试随内核退役。

### 6.2 合并冲突裁决
`merge-loop` 测的是「两条 lane 冲突时由 merge Agent 裁决」。
v2 无此能力，**该测试无法机械迁移**。

- 保留 → 需在 v2 实现冲突裁决（注意审计要求保留 merge 能力，不能随内核删掉）；
- 丢弃 → 该类测试随内核退役。
