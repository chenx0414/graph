# Graph v2 管理入口

完整契约见 [已确认规格](../specs/graph-rebuild-v2.md)。

## 先选形状，再写节点

写第一个节点前先回答三个问题，并把答案写进 `summary` 或 `decisions`：

1. **这些子任务能并行吗？** 互不依赖 → 扇出与汇合；有先后产物依赖 → 顺序执行。
2. **要不要多个独立候选？** 需要比较、打分、按硬性条件裁决时，先派 N 个候选，再用 `jury` 模块按硬性条件与加权排名决出胜者；不要把候选交给一个"评审"节点凭印象挑。
3. **哪一步不可逆？** 改数据、发版本、对外承诺的那一步之前放 `graph.human_check`，而不是在流程末尾统一加一道人确认。

真实可用、但历史提案几乎没用过的形状：`router`（两层子图路由，只投递命中的分支）、`fanout` 汇合锁存（`once`，跑下一批必须显式 `reopen`）、`jury`（多视角评委）。定义见 `examples/graphs/` 与 [原生定义示例](graph-v2-02-原生定义示例.md)。

## 每多加一个节点，说出它带来的新信息

节点不是流程装饰。加一个节点之前先写一句话：它产出哪条上游拿不到的信息。写不出来就删掉它。

`propose_graph` 与 `validate_proposal` 会回读草案并给出 `shapeNotes`（建议，不是拒绝）：某个节点在 `summary`/`decisions` 里从未被提到、两个节点用同一个 `recipe` 与同样的 `task`、某个节点没有连到任何输入、输出或边。被点到名的节点，要么在 `decisions` 里补上理由，要么删掉。
