# ADR 0030：Graph v2 内核以接口投递为正式执行模型，旧内核整体废弃

日期：2026-10-01

## 状态

已接受（使用者决定：见下）。正式规格在 GitHub Issue #1；本 ADR 只记录**决策与对既有 ADR 的影响**，不重复规格正文。

## 背景

现有内核是一个 DAG 调度器：节点用 `dependsOn`/`when`/`loops` 声明依赖，图的 read
iness 由成功状态计算，分支由一个单 case 的路由动作决定，提交通过 `submit_result` 回调落账。
这一套在动态返工、多输入汇合、模块可解释性上已经开始不够用：它不是「谁向谁投递了什么」的模型，
而是「谁依赖谁完成了」的推断模型。

Issue #1 给出了从第一性原理重写的产品契约：agent 有具名逻辑接口；边定义连接；投递承载一次信息；
模块执行控制逻辑；子图复用结构。正式执行模型是**接口投递**，不是依赖推断。

使用者对本 ADR 需要记录的两个问题直接给了答复（2026-10-01）：

1. 交付范围：全套 Issue #1 第 13 节 8 阶段，不使用 Graph 任务图，由 main agent 单点 RSI 实施。
2. 切换方式：「丢弃旧内核，统一走新内核，之前的 graph 都丢弃不要」。

## 决策

1. **新内核只有一条执行路径。** 新建 graph、执行、路由、提交、恢复全部走 v2 内核。
2. **不做新旧并存，不做转换命令。** 旧 DAG 调度器与旧 graph 历史在切换点整体废弃。
   这比 Issue #1 第 13.8 节写作时假设的「旧运行跑至停稳再归档、长期只保留新路径与必要历史 reader」
   更激进：不再需要双调度器共存、不需要旧图到新图的转换器、不需要为旧执行保留历史 reader。
3. **复用而非重建基础设施**（Issue #1 第 11 节）：预算账本、调用记录、能力库/配方编译、模型目录、
   Git worktree、会话分页、HTTP/SSE 继续复用。新内核的持久层建在**同一个** SQLite 数据库上
   （见 `src/core/kernel-store.ts`），不另起第二个存储。
4. **切换时点**：Phase 8。在此之前新内核只作为库内实现与测试存在，产品行为不变。

## 与既有 ADR 的关系

- **ADR 0004（Agent 实例与节点一一对应）**：继续适用。返工回到原节点、原实例，保留会话与累计额度；
  新内核用 Execution 轮次区分一次返工。
- **ADR 0011（每 operation 一个独立 Pi 进程）**：**被取代**。新内核是**每节点一个常驻 Pi 进程**，
  在一个进程内接受 `start-turn`/`inspect`/`close` 直到图结束；能力/身份变更在 turn 之间受控重建进程。
  常驻性与配置重绑已由 spike 实测（`docs/agent/issue-1-phase1-spikes.md`）。ADR 0011 的 bundle digest、
  manifest v3、rebind 机制继续复用；只有「进程生命周期 = 一次 operation」这一点被取代。
- **ADR 0025（共享产物工作区）**：不可变版本继续适用；作者/修改者权限按 Issue #1 第 2 节调整。

## 后果

- 好处：执行模型与可视化对象一一对应（投递就是边上的事实），返工/汇合/模块都能回溯；
  不需要维护两套调度器。
- 代价：切换点是一次破坏性替换。旧 graph 及其历史整体丢弃，**不可恢复**；
  删除旧内核代码前必须列出被删模块清单并复核无活跃引用。
- 风险：切换发生在用户可见阶段，需在实施时给出明确时机与迁移说明。
