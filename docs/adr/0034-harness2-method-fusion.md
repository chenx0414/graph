# ADR 0034：Harness² 的融合方式——移植方法内核，不部署其本体

日期：2026-10-22

## 状态

已接受。

## 背景

Harness²（[google-research/harness2](https://github.com/google-research/harness2)，Apache 2.0，
论文 arXiv:2610.14224）提出让 harness 自我改进的两层递归：任务级的
**Propose–Probe–Compose**（提出 harness 改动 → 在同一任务上探测其效果 → 从行为对比里合成更好的 harness），
以及 Harnessing 级的**经验库**（按领域沉淀采纳过的 harness 与教训）。

Graph 已有自己的 RSI（[ADR 0026](0026-main-agent-recursive-self-improvement.md)）：Main Agent 改
Graph 自己的源码 checkout、跑项目门禁、提交到 `rsi/*` 分支、请求热重载。执行者与改进者是同一个 Agent，
改动对使用者可见可审计。

问题是：Harness² 与 Graph 的 RSI 是什么关系？是可以把 Harness² 装进 Graph，还是只能借鉴？

评估结论见 [Harness² 评估与融合方案](../agent/harness2-fusion.md)。关键事实：

- Harness² 是**面向基准跑分的研究框架**：Python 3.12 + uv、只支持 Linux、依赖 Vertex AI，
  求解器跑在 OpenCode / Codex 上，评测对象是三个公开基准。它的 harness 树是给基准求解器准备的文件树。
- Graph 的产品后端是 Go 进程（`graphd`），执行内核是 PiG；它的 harness 一半是声明式文件
  （`~/.graph/prompts/` 的 12 个文件、skills、配方、能力包），一半是宿主代码。
- Harness² 刻意**放弃标准答案**，因为它要跨基准泛化；Graph 是生产产品，有确定性门禁、验收与人工确认。
- Graph 已经具备 Harness² 假设缺失的东西：一张图就是"同一任务的多个候选并行跑"，
  执行事实、产物、用量都落盘，且有 `scripts/harness-real-eval.mjs` 等离线评测设施。

Graph 真正缺的不是"再跑一遍 harness"，而是**把多个候选的结果放在一起比较**，
以及**把采纳的结果连同依据沉淀下来**。

## 决策

- **不部署 Harness² 本体，不引入 Python/uv/Vertex 依赖，不引入第二套执行底座。**
- **移植其方法内核**，并在 Graph 原生运行时里实现三件套：
  1. **对比式 Probe**：同一任务的多个候选跑完后，宿主读出每个候选的行为事实
     （执行状态、提交内容、工具调用与失败、token、耗时、最终答复），给出与基线的行为差异，
     并把候选**匿名化**（A/B/C…，同一图内映射稳定）。
  2. **无标准答案的裁决**：对比只给事实，判决留给 Agent；裁决连同 **cue / lesson / evidence**
     写进领域经验库。缺证据的经验不收——没有依据的教训会教坏下一个任务。
  3. **经验召回**：某领域已采纳的经验随对比结果一起返回，也可单独读取。
- **匿名是刻意的**：能看到"哪条车道产出了哪个答案"的选择者会按车道选，而不是按答案选。
- **不改变现有 RSI 的定位**：代码级改进仍走 `apply_rsi_change` 与确定性门禁；
  本决策新增的能力是 harness **行为**层面的比较与沉淀，两者互补而非替代。
- **经验库存放在既有制品体系里**：`plans/harness-experience-<domain>`（schema
  `graph.harness-experience@1`），写用 Agent 自己的制品通道，读用宿主侧制品库，
  提升到项目作用域。跨项目不共享，与"项目共享产物"的既有边界一致。
- **不新建第二个权威状态库**：经验落在 `artifacts` 表，事实读自
  `kernel_executions` / `kernel_submissions` / `node_entries` / `kernel_provider_calls`，
  不新增 schema 迁移。

## 后果

- Main Agent 多三个工具：`compare_harness_candidates`、`record_harness_decision`、
  `read_harness_experience`，只对 main 开放。
- 一张图跑出多个候选之后，Agent 可以按"行为差异"而不是"感觉"选，
  选完的教训会在同项目下一个同领域任务里出现。
- Graph 与 Harness² 的关系从"要不要装"变成"方法怎么落地"，
  后续 P2（探针驱动器）、P3（双轴提案与合成）、P4（经验进上下文）、P5（评测脚本进闭环）
  都建立在本次的三件套之上，详见评估文档。
- 代价：新增三个工具面与一处制品约定；对比结果是**事实**，
  它不替代既有门禁与人工验收，也不应该被当成质量证明。

## 与既有决策的关系

- [ADR 0026](0026-main-agent-recursive-self-improvement.md) 决定 RSI 改 Graph 源码、走门禁、热重载：
  本决策**不改变**它，只在其旁边补上 harness 行为层面的比较与沉淀。
- [ADR 0030](0030-graph-v2-interface-delivery-kernel.md) 决定 graph 入口统一走新内核：
  本决策的对比与裁决都跑在新内核的正式事实之上，不新增平行执行路径。

## 2026-10-22：探针驱动器与节点级 harness 覆盖

第一段落地（对比 + 裁决 + 经验库）之后，剩下的问题是"多候选谁来组织"：
Agent 要自己建图、派发、等节点、再调对比，实验本身还要用户确认草稿。

决定：

- **节点定义新增可选的 `harness` 覆盖**：`{"<提示键>": "<文本>"}`，只允许替换
  `agents/<definition-id>.md`、`rules/<role>.md`、`tools/<role>.md`、`runtime/node.md`。
  它改变"Agent 被告知什么"，不改变宿主强制的权限、闸门与预算——与 ADR 0026 的分界一致：
  那是宿主的事，这是 harness 的事。
- **覆盖必须落在会话真正读的那份提示库上**：`AgentContextLibrary.WithOverlay` 返回一份带覆盖的库副本，
  节点泳道把它交给该节点的会话。只把覆盖写进执行快照（`prompts`）是不够的：
  模型读的是库，快照只是冻结记录，两者不一致时模型会读到旧文本。
- **新增 `probe_harness` 工具**：宿主建一张内部图（每变体一个节点，同一任务、同一输入、
  不同 harness），派发、等待候选停稳，产出与 `compare_harness_candidates` 同形状的对比。
  探针图由宿主创建，不经用户确认的草稿：它是一次实验的结构，不是要交付给使用者的产物结构。
  它照样占用全局执行名额、照样计入预算、照样落盘成可审计的执行事实。
- **不新增状态库**：变体随图定义走，对比事实读内核既有表，经验落在既有制品体系。

## 2026-10-23：让 Agent 读得到自己的证据

RSI 身份文本要求 Agent"观察自己的轨迹、工具错误、被挡住的 operation 与检查结果"，
但没有任何工具让它读得到这些：事实都在（`node_entries` 的 transcript、`message.tool` 事件、
`tool_calls` 统计、`questions` 的内部问题、`kernel_queue` 的失败原因、`rsi.change` 回执、
`invocations` 的用量），只是没有面向 Agent 的读接口。

决定：

- **新增 `read_harness_evidence`**：把一次运行的证据读成一份有界的摘要，并可按节点、按
  轨迹逐步读取。它是**读**，不写任何东西，也不代替既有门禁。
- **摘要只给事实**：哪个工具失败了、失败几次、什么被挡住了、上次检查如何、花了多少。
  判决仍然属于 Agent——这与"对比不给判决"是同一条界线。
- **两种记录形状都读**：图里的节点写 transcript entries（带失败原因），
  会话里的主 Agent 只写事件（带工具名与错误标记）。只读一种会让另一类运行读不到自己的失败。
- **失败原因可能读不到**：会话里的工具失败只有工具名与摘要，原因只存在于模型当时看到的
  上下文里。摘要因此如实给出"哪个工具失败了几次"，不编造原因。
- **身份文本同步**：RSI 身份明确要求先读证据再决定改什么，并提到 `probe_harness`。
- **裁决记录要能读**：匿名字母只在它来自的那次对比里有意义，隔一阵再看这条经验就不知道
  当初选了什么。宿主把字母解析回真正跑过的那个候选（对比里的匿名 id 按节点 id 排序分配，
  解析是确定的），记录里存的是候选的名字。

## 2026-10-23：双轴提案与按轴沉淀

Harness² 的任务级递归有两条提案轴：INV（对每个任务都成立的不变式）与 DOM（这个领域的特化），
两条轴各自被探测，再从行为对比里合成。

决定：

- **探针的每个变体带一个轴**：`general` 或 `specific`。一次实验提两个轴，对比会显示哪一轴划算。
- **教训按轴落在不同的 scope**：`general` 的 scope 名为 `general`，**每个领域都读它**；
  `specific` 的 scope 是该领域自己的，只有它读得到。这是 INV 在 Graph 里的对应物：
  一条对任何工作都成立的经验，只有在每个领域都能被读到时才算真的通用。
- **不写轴就是 `specific`**：跨领域的分量要靠证据去claim，不能顺手写。
- **合成留到后面**：把两轴的赢家合并成一份 harness，需要一个"两轴都赢时怎么合"的规则，
  而这要等经验库攒够真实条目之后才知道该怎么定。
- **但对比要说得清差异的来源**：对比现在报告每个候选**跑在什么 harness 下**
  （节点声明的提示覆盖）。只有行为差异、没有差异来源，合成就无从下手：
  看到"候选 A 改了 rules/worker.md 的第 3 段"和"候选 B 改了整个文件"，
  才谈得上把两者合成一份。这条不预设合成规则，只保证合成时有材料。

## 2026-10-23：通用教训进 system prompt

沉淀下来的经验原本要靠 Agent 主动调用工具才看得到——它得记得调、得挑对领域、还得读完。
下一类任务因此常常从零开始。

决定：

- **宿主在装配主 Agent 的 system prompt 时自动注入通用教训**：rules 段新增一个生成型部件
  `rules.experience`，内容是 `general` scope 的教训，每条一行（情况 → 做法 → 依据），
  排在 host 规则之前。注入点与既有的 `rules.host` 同构，不改装配顺序。
- **只注入通用轴**：宿主不知道一个任务属于哪个领域（`tasks` 表没有领域字段），
  而通用轴的定义就是"对任何一类工作都成立"，天然不需要领域。领域教训仍由
  `read_harness_experience` 读取。
- **注入的是上下文，不是指令**：它说发生过什么、依据是什么，不说必须怎么做；
  权限、闸门、预算一概不动。条数有上限（5 条），每条文本有长度上限。
- **只给主 Agent**：改进 harness 的是它，节点拿不到"这个项目学到什么"的判断力，
  而把教训传下去是主 Agent 编排的事。
- **TypeScript 侧未同步**：产品后端是 Go 进程，TS 守护进程正在被退役，
  这次不为它再实现一遍注入。

## 2026-10-23：摩擦与教训合为一个库

原先有两套 harness 知识：`harness-backlog` 制品（待办的摩擦，靠身份文本约定手工维护）
和经验库（已采纳的教训，宿主拥有）。两者是同一条知识的两个阶段，却住在两个地方、
用两套规矩记，于是"我遇到过什么"和"我最后怎么做"永远对不上。

决定：

- **一个库**：条目有两种 `kind`——`friction`（遇到、还没解决）与 `lesson`（采纳了、有依据），
  各有自己的 `status`（friction: open / fixed / rejected；lesson: adopted）。
  读的时候是**一份列表**：该领域自己的条目 + 普遍适用的那些，每条自带 axis 与 kind。
- **只有已采纳的教训进 prompt**：摩擦是怀疑。把怀疑当事实注入下一次任务，是把噪声升级成指令。
  身份文本里的 `harness-backlog` 制品约定随之退役（既有的 backlog 仍然可读）。
- **摩擦有状态**：同一个 cue 再记一次就是更新它（`status: fixed` + `ref`），不是新增一条。

## 2026-10-23：接续上一轮，以及把领域交给宿主

合成（两轴都赢时怎么合）的前提是**每一轮都从上一轮的赢家出发**。否则每轮都在原点重写，
改进不累积。

决定：

- **采纳的教训留住它跑在什么 harness 下**：裁决记录带上该候选的提示覆盖（`overlay`）。
  教训因此不只是话，而是**可复用的 harness**。
- **探针可以以已采纳的 harness 为基线**：`baseHarness: "adopted"` 让每个候选从它起跑，
  变体叠在上面。于是"基线 vs 基线+一个改动"就是一轮递进的实验，
  而不是每次都从默认提示重写覆盖。
- **对比报告每个候选实际跑的 harness**（合并后的）：差异的来源看得见，合成才有材料。

P4b（领域教训也自动在场）的前提是**宿主得知道这个项目是做什么的**。此前 `tasks` 表里没有领域字段，
Agent 自己报的领域只有它自己用得上。

决定：

- **领域由 Agent 声明、项目级保存**：`declare_harness_domain` 把领域写进项目作用域的
  `plans/harness-domain` 制品。一个项目干的活不会因为换了个会话就变样，所以领域属于项目而不是任务。
- **注入 = 该领域的教训 + 普遍适用的教训**：宿主在装配 prompt 时读回项目声明的领域，
  把两个 scope 的已采纳教训都带上。

## 2026-10-23：写进哪个 scope，就得先读哪个 scope

经验库是"读—改—整份重写"的模型：写入前先读出那个 scope 的条目，再把新条目并进去，
然后发布新版本。所以**读回来的必须是即将被写的那个 scope**。

此前的接线把 `scope` 丢了：录制路径要读某个 scope，读回的却是"这个领域 + 通用"，
于是每次写入看到的都是空库，**新条目会盖掉这个 scope 里之前的条目**——
库里永远只剩最后一条。E2E 之前没发现，是因为它只往一个 scope 写一条。

决定：

- 接线必须传 `scope`；`HarnessExperience` 的 scope 优先于 domain。
- 回归由真实 E2E 守住：往同一个 scope 写两条，读回来必须是两条。

## 2026-10-23：闭环端到端验证

前面几段各自有 E2E 证明，但没有一个跑通整条链。新增的 `tests/e2e/harness-loop.test.ts`
在一次运行里走完：一次失败的工具调用 → 读自己的证据 → 两个 harness 的探针对比 →
按通用轴记录裁决 → **下一个任务（同一项目、另一个对话）的 system prompt 里已经在场**。

这条链现在是可验证的，而不是可推断的。

探针还多了一件事：**它收掉自己建的图**。探针是实验，不是要交付的结构；留着
一张永远停在 running 的图，会在项目里堆出"永远在跑"的条目。
