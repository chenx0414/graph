# ADR 0021：能力绑定即默认运行授权

日期：2026-09-19

## 状态

已接受。

## 背景

能力被 Agent 配方绑定并加载后，运行时仍要求网络 MCP 的每次工具调用匹配独立的
`mcp:<capabilityId>:<toolName>` 任务 grant。结果是 Main Agent 和 subagent 都能在
`tool.md` 中看到工具，却无法直接调用；用户会收到一个无法体现真正产品选择的权限问题。

Pi extension 还只获得入口文件的沙箱读取权限。像 `agent-browser-native` 这样入口依赖
同目录 `./lib/*` 和包内脚本的扩展会加载失败，能力记录却仍显示“已加载”。

## 决策

- 默认运行模式为 capability bypass：把能力绑定到版本化 Agent 定义，就是该 Agent 调用
  该能力已经发现工具的运行授权，不再要求逐工具 grant 或用户确认。
- 规则统一作用于 Main Agent 和所有 subagent；它们使用同一能力加载、工具暴露和执行门。
- MCP 的 `networkDomains`、`networkAccess`、进程沙箱、工作副本边界、预算、暂停和调用
  计量继续生效。绑定能力不扩大这些边界，只消除重复的逐工具授权。
- Pi extension 的能力快照目录作为只读根挂载到独立 Pi worker。入口文件和包内依赖都能
  加载；入口文件本身仍必须是能力目录内的受限路径。
- `permission` 问题继续保留给配置边界之外的真实用户决定，例如新增外部写入范围或人工
  验收；不再用于已经绑定能力内部的普通工具调用。

## 后果

用户配置到 Main Agent 或 subagent 的能力会真正可调用，不再出现“能力已绑定但没有可调用
入口”或“只读调用被任务授权拦住”。如果用户不希望某个能力可用，应移除配方绑定或卸载能力；
运行中的实例仍按原定义版本执行。

代价是能力绑定的安全含义更强：安装、绑定和调用之间的确认次数减少。域名声明、OS 隔离、
调用计量和审计仍是主要防误用边界。
