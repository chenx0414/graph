# ADR 0029：确认过的检查可以声明走出沙箱（仅在完全访问下）

日期：2026-09-30

## 状态

已接受（使用者决定：让这道门能声明不走受限进程）。

## 背景

形状 A 的门「全量测试」跑项目自己的套件（`node --run check`）。实测（任务 `68543fed`，**同一份集成副本、同一条命令**）：

- **不进沙箱**：1480 / 1480 通过，127–145 秒；
- **进沙箱**：**224 失败 / 49 通过**，以套件自身的超时为主（15s×40+、60s×6），另有一批毫秒级全挂的用例。

即沙箱让每个子进程都慢到套件自己判超时。**一道因为与工作无关的原因而红/绿的门，证明不了任何事**——它比没有门更糟，因为它会被当成结论。

同时，这道门在隔离上比它要证明的东西**更严**：完全访问下 agent 本来就可以跑宿主命令（`commands: 'host'`、宿主文件系统），而门的命令来自**已确认的图**（不是 worker 当场写的），并且要等到三个评审都通过、merge 整合完之后才跑。

## 决策

- `graph.command` 新增可选 `sandbox: boolean`，**默认 `true`**（保持原状：在操作系统沙箱里、按 `workspace-command.ts` 的授权跑）。
- 声明 `sandbox: false` 时，命令**直接以宿主进程运行**：继承宿主环境（PATH / HOME / 凭据 / 真实的临时目录）、自成进程组（超时按组收割）、输出有界截断。**不使用**沙箱专用的 loopback 解析 shim，也不套用命令白名单。
- **只有在完全访问（`isFullAccess`）下才被兑现**。非完全访问下一律**拒绝**，并在节点问题上写出原因（`adapter_error`），**绝不悄悄降级**成沙箱内运行——作者写着 `sandbox: false` 却拿到一次偷偷换了形态的运行，比直接拒绝更危险。
- 声明必须是布尔；其他值一律拒绝。
- **记录里写清它怎么跑的**：`checks/<nodeId>.json` 带 `sandboxed: true|false`。同一道命令在沙箱内外含义不同，读证据的人不必靠推断。
- 超时仍由节点的 `timeoutMs` 声明（HB-220），被切时记录写明是 harness 的上限而不是命令的判决。

## 后果

- 项目的整套测试可以重新成为一道**真的门**：在完全访问下按项目自己的方式跑，沙箱外的语言与它会证明的东西一致。
- `sandbox: false` 是图能声明的最强的一件事：它交出的是**工作副本之外**的写权限与宿主环境。它换来的是「证明权仍然在 harness 手上」——门由 harness 跑、结果由 harness 记，agent 的话依然不是证明。
- 授权面因此收窄成两句话：**谁**能声明（已确认的图，且宿主处于完全访问），**记录**说了什么（`sandboxed`）。非完全访问下这道声明不可用，这一点由代码拒绝保证，并有测试钉住（`tests/console/program-check-sandbox.test.ts`：标准访问下拒绝并说明原因；完全访问下真的在沙箱外跑——以宿主环境变量能否到达子进程为证；不声明时仍在沙箱内；非布尔被拒）。
- 与 ADR 0024（完全访问策略）一致：完全访问本就是「agent 可以跑宿主命令」的档位；本 ADR 只是让**已确认的机械门**也能站在同一档，而不是比被它检查的东西更受限。
