# main 与 Graph 节点迁移至 pi-durable 1.1.0

## Problem Statement

Graph 自建的 Agent 进程、轮次和恢复机制在真实返工、动态修改和重启时存在故障风险。用户要求将内核换成 pi-durable 1.1.0，并明确 main 与节点统一迁移；旧 graph 执行历史可以清空，main 会话和配置必须保留。

## Solution

以锁定版本的 durable Harness、持久会话和任务执行 main 与节点。用户继续通过现有界面和接口管理 Graph，接口投递、模块、子图、返工、共享产物、权限、累计预算与独立验收继续成立。恢复使用持久执行事实，副作用不明确的工作交 main 处理。

## User Stories

1. 作为用户，我希望已有 main 会话保持身份、消息顺序和内容，以便切换后继续同一项工作。
2. 作为用户，我希望模型、凭据、能力、配方和权限配置保留，以便迁移不要求重新配置。
3. 作为用户，我希望 main 与节点使用同一执行机制，以便恢复行为一致。
4. 作为 main，我希望节点沿用稳定会话和累计额度，以便返工回到原 worker。
5. 作为 main，我希望所有具名输出整体校验后受理，以便错误输出不产生部分投递。
6. 作为节点，我希望接口输入和直接聊天按受理顺序串行，以便不存在两个轮次同时修改我的工作副本。
7. 作为 main，我希望动态改图保留已受理投递，以便修改连接不丢失已发送的工作。
8. 作为节点，我希望当前轮次采用冻结的 instructions、skills、模型、权限与工作位置，以便中途修改不改变正在执行的任务。
9. 作为 main，我希望更新后的节点配置在下一轮生效，以便原地调整同一 Graph。
10. 作为用户，我希望重启后待执行工作可以继续，以便不靠手工重建图恢复。
11. 作为 main，我希望副作用结果未知时有明确问题与证据，以便核对后处理而非盲目重跑。
12. 作为用户，我希望暂停、停止、完成请求和 main 停驻保持各自含义，以便控制不会因重启而失效。
13. 作为用户，我希望预算、用量证据和调用历史继续累计，以便恢复不会重置额度或把未知用量记为零。
14. 作为节点，我希望绑定的 Skills、MCP、扩展和工具实际可用且受既有权限约束，以便迁移不丢失能力。
15. 作为审查节点，我希望审查已集成的真实代码，并保留同轮次证据，以便验收与最终提交一致。
16. 作为用户，我希望产物仍有不可变版本和精确引用，以便旧成果及来源仍可信。
17. 作为 main，我希望 artifact_list 仍只列当前 graph 的共享产物，以便没有跨图泄漏。
18. 作为用户，我希望可复用 Matt 团队继续完成 plan、实现、独立审查、原 worker 返工，以便团队模板不因内核替换失效。
19. 作为用户，我希望清理只针对旧 graph 执行历史，以便 main、草稿、配置、成果和代码不被误删。
20. 作为用户，我希望默认桌面应用实际加载新内核，以便源码验证通过后的交付可以直接使用。

## Implementation Decisions

- durable、pi-ai 及需要的同系列依赖锁定兼容的 1.1.0 版本；依据发布 tag 和 npm 包，不依据上游 main 推测 API。
- durable 负责 Agent 会话、模型与工具执行的持久 checkpoint、任务调度及恢复。Graph 保留接口协议、投递、模块、图修订、工作副本、权限、预算账本和验收的领域规则，不保留第二套 Agent 执行恢复器。
- main 位于 graph 外，长期会话独立于 graph 生命周期；每节点具有稳定会话映射，返工不创建替代节点或重置额度。
- 同一正式 SQLite 数据库存放命名空间隔离的 durable 记录和 Graph 领域事实，单一宿主持有 durable 存储。首先证明适配器的事务、连接所有权与存储契约，再接入用户数据。
- durable 输入受理与 Graph 输出提交使用不同内部术语和身份映射。业务命令使用稳定身份幂等受理；受理后崩溃再恢复不产生重复投递、模块触发或账本结算。若用持久 outbox，其保存的是命令，Graph 业务记录仍是领域事实权威。
- 运行配置按 Graph execution 冻结；durable 的每 phase registry snapshot 不足以满足此契约。重启必须重新加载该轮次实际采用的能力版本，而非自动采用最新配方。
- 工具按实际副作用选择重放规则。无法证明幂等的外部操作中断后保留证据、产生由 main 持有的问题；只取消等待不能冒充停止任务。
- 用量证据等级、发送前额度预留、未知用量、模型切换和累计预算继续由 Graph 账本管理，禁止新增绕过权限或预算的模型请求通道。
- main 历史转换保持可见消息身份、顺序、正文及必要工具上下文；转换幂等，不重新执行历史模型和工具调用，不重复计费。保存原始历史与可恢复备份。
- 切换时停止旧执行入口，退役旧 graph 在途执行并清理其执行历史；保留定义与草稿、main 会话、配置与凭据、能力与配方、共享产物、工作副本及 Git 成果。无需恢复旧 graph 在途执行。
- 最终删除旧 Agent 执行和恢复路径，更新运行说明及默认应用。实施阶段可在隔离集成分支采用 expand–contract，正式应用不提供旧内核回退执行入口。

## Testing Decisions

- 主要验收面是现有公共 HTTP/runtime 接口，使用真实 durable 发布包、磁盘 SQLite、可控制响应的真实 HTTP 模型服务及真实工具工作副本；观察用户可见消息、投递、成果、问题和账本，不断言内部方法调用。
- 存储适配额外运行上游 conformance；验证命名空间不改写 SQL 字面量、异常不关闭宿主连接、事务失败回滚、异步提交不混入其他领域写入。
- 沿用现有 main 会话、接口投递、动态改图、预算、权限、产物和 Git 验收的高层测试形式，改用真实 durable 执行，不以预先写好的成功结果代替模型与工具路径。
- 用子进程强制终止验证受理前后、工具副作用前后及结果提交前后的恢复；区分 graceful close 与崩溃。验证无重复业务效果、未知副作用报告以及原会话继续。
- 验证当前配置冻结、下一轮生效、原 worker 返工、独立审查在 producer 集成完成后读取真实 HEAD；同一节点并发输入保持串行。
- 在用户数据库副本验证 main 转换、旧 graph 清理范围与重复迁移；正式切换前保留备份并确认没有旧执行在途。
- 完整检查、应用构建后，驱动默认桌面应用完成 main → planner → worker → 独立审查 → 原 worker 返工，并验证真实重启恢复。

## Out of Scope

不恢复旧 graph 的在途执行；不改变接口投递为 DAG；不重设计界面或预算政策；不删除共享成果、用户代码和 main 历史；不升级至浮动最新版；不把任意外部副作用承诺为 exactly-once。
