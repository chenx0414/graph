# 以主 Agent 为入口：产品改造草案

日期：2026-09-14。来源：用户要求像与 Pi 聊天一样，先与主 Agent 交流、理解问题、共同制定 Graph 策略，再开始执行。本文为具体改造方案，尚未实施，不覆盖或修改任何分支。

## 产品目标

用户打开产品先面对一个可以持续交流的主 Agent。它能阅读所选项目的事实、追问缺失条件、提出不同方案、解释任务安排，并在执行过程中继续接受问题和修正。Graph 是双方商议结果的可视化与执行工具。

首次开聊不要求用户先填完项目和任务主题。可以先表达模糊目标；需要查看代码时，主 Agent 协助定位并绑定项目。执行仍针对一个明确的功能任务，新增功能遵循已有独立任务规则。

## 现状依据

原始 `docs/graph-mvp.md` 已要求“与使用者讨论并形成可验收说明”，CONTEXT.md 将主管定义为直接与使用者对话的 Agent。因此这是核心产品体验的补齐，不应只做成换皮聊天输入框。

当前存在 Web/桌面界面、Pi 会话、主 Agent、say/accept、图及持久执行内核，但有结构缺口：

- `user.begin` 要求 projectId 和 request，主 Agent 生命周期依附已创建的任务。
- `user.task().say` 将所有消息计入 requirement_version，确认后统一 requirements_locked。询问进度/解释策略也没有独立消息语义。
- TaskView.messages 只来自 task.created 和 requirement.changed，缺少完整 assistant/工具交互记录；当前UI所谓conversation只是需求文本列表。
- 主 Agent 提示直接要求 propose_graph；未明确区分交流、调查、策略比较、生成可执行提案。
- 确认后的调度仅包含已确认图的节点，没有可靠保证讨论用主 Agent 始终能作为用户的对话入口。

上述能力与main已验收的执行内核可以复用。此前T01–T08阶段通过不应被解释为这项主Agent体验已经完整落地。

## 用户应看到的流程

1. 打开会话，直接说想解决什么，也可以只说“这个项目很乱，先帮我看看”。
2. 主 Agent 帮助选定项目，在已有读取范围内调查结构、现状、问题和约束；明确哪些结论来自文件/运行证据、哪些还待确认。
3. 主 Agent 用自然语言讨论目标、范围、方案取舍、风险、验收方式和模型/预算安排；信息足够时直接推进，不机械地轮流问固定问题。
4. 逐步形成一个可见、可修改的策略草稿；用户可以说“先做验证，再决定是否重构”“不要并行改这个模块”。图和策略说明同步更新。
5. 用户确认当前完整提案后，开始正式执行。确认卡绑定项目、版本、范围、目标分支、额度和验收项；查看或解释草稿不会启动工人。
6. 执行中保持同一对话：询问进展、解释某个节点、指出偏差、暂停、补充证据。主 Agent 基于实际事件作答，并将需要改变范围/额度的请求转为可审核的变更。
7. 完成后主 Agent 说明成果与证据，仍可继续讨论；新的功能建立关联的新任务。

“只讨论/先看一下”允许受控调查，不允许自动实现、修改业务文件、派发工人或合并。需要验证性写操作时纳入具体可审阅的调查步骤，不能借讨论模式绕过既有权限。

## 关键设计

### 会话与任务分开

新增持久 Conversation 及其主 Agent 会话；它可以尚未绑定任务。项目选择和功能任务在交流中建立关联。对话消息有稳定ID、角色、轮次、引用、状态和时间；请求重试不得重复触发模型或图动作。

主 Agent 对同一功能任务持续保留上下文，不因确认提案就消失。跨功能任务保留可追溯的决策摘要和引用，遵循“新增功能单独任务”规则，不混用任务权限或额度。

未创建功能任务的主 Agent 调查也有宿主明确的用量与权限归属；不能产生无账本模型调用。主管属于现有全局Agent并发上限，交互请求可优先排队，不得绕过凭据/预算门。

### 消息与正式变更分开

普通聊天不增加需求版本。主 Agent 解释状态不修改图；提出草稿只更新草稿。正式修改需求、图、预算或权限必须调用各自受校验的命令，形成事件。

执行中的消息进入持久队列。主 Agent 忙时可继续输入，明确显示消息已接收/待处理；不会覆盖上一条或丢掉快连发消息。重启后可恢复。停止生成、暂停任务、取消一个未执行提案是不同操作，UI应明确表达。

### 对话、策略与执行状态可同时查看

主区域是完整用户/主Agent对话，显示实际调查工具的摘要与来源；不伪造隐藏推理或把内部思维链作为功能要求。侧边是当前目标、约束、待决事项、策略草稿和图；执行时显示真实状态与证据。

即时文字流和最终消息分别处理：流可重连，最终消息须有正式记录；工具状态与模型回复去重、不串任务。用户不需要操作JSON、数据库或harness。

### 主 Agent 的工作方式

提示和工具职责应支持“理解 → 调查 → 讨论取舍 → 策略草稿 → 提案确认 → 指挥与解释”。不强制每次用户发言都产图；小问题可以直接回答，小任务可以选择简短流程。方案基于发现的事实，允许明确指出用户方案的问题。

复用现有Pi及Graph内核，不要求为了聊天入口引入新编排框架。自然语言表达可以触发草案；执行授权由确认动作落到具体版本，不能从普通赞同或策略讨论中暗推扩大授权。

## 按优先级交付

| 优先级 | 项目 | 交付与验收重点 |
| --- | --- | --- |
| P0 | 主Agent完整双向会话 | 自由多轮聊天、最终assistant消息持久化与流式呈现、刷新/重启恢复；不要求先建功能任务 |
| P0 | 调查与共同规划 | 项目定位、读取证据、针对性追问、方案比较；“先讨论”下工人派发/业务写入为0 |
| P0 | 草稿到执行的确认边界 | 策略与图可迭代，确认绑定当前版本；旧提案不能执行，普通聊天不改需求版本 |
| P0 | 执行中的持续对话 | 确认后仍能问进展/原因、发修正；消息可排队，范围改变走明确变更，主Agent始终可找回 |
| P1 | 决策与上下文连续性 | 记住已明确的目标/约束，引用来源；长会话摘要、任务切换和历史不串数据 |
| P1 | 可视化协作工作台 | 对话为主，策略/图/证据辅助；从项目调查到交付全程无需代码或脚本 |
| P1 | 真实入口整体验收 | 从首次启动到模糊目标、多轮讨论、确认、运行中改主意、恢复和交付的浏览器全流程 |

建议先交付一条完整纵向流程，再扩展面板和记忆功能；每项不能只靠组件截图或模拟文本宣布完成。

## 必须用来验收的对话场景

1. **模糊需求**：“我想改善这个项目，但还没决定做什么。”主Agent调查/交流后给出有依据的候选，不能自行启动实现。
2. **约束协商**：“先做最小可用版，预算有限，登录先不改。”连续多轮后提案仍保留约束，并解释拆分和模型选择。
3. **推翻草稿**：“刚才那个方案先不要，改成先验证性能瓶颈。”旧草稿失效，既有工人派发为0；后来的确认只执行新草稿。
4. **确认后问问题**：“现在卡在哪里？为什么要两个审查节点？”正常对话返回当前真实证据，不触发requirements_locked，不重复工人操作。
5. **运行中改变目标**：“顺便加上另一平台。”主Agent解释影响，形成新任务或需确认的变更，不能静默改现有验收项。
6. **暂停与恢复**：“先停一下，我们重新讨论。”立即受理暂停命令；已在途调用按既有门和核对规则处理。讨论仍可进行，恢复遵循最新已确认范围。
7. **持久性与排队**：主Agent运行时连发三条说明、断网重连、应用重启，不丢消息、不重复模型派发、不错误复用旧提案；显示可观察的处理状态。
8. **完成只等用量/返工中核对**：原PA02系列全部保持，不能因引入聊天层退化状态、费用或轮次隔离。

脚本化provider验证协议，真实浏览器验证用户流程；主Agent是否会理解、追问与解释需要另以一轮有界真实模型对话评估。不要以模型请求数量、能生成JSON或静态聊天截图代替交互验收。
