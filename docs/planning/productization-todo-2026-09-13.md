## T01 · 统一启动与首次运行入口

**任务说明**：提供正式命令、稳定数据目录和明确访问地址，使作者能够启动 Graph，而不需要手写脚本调用 `openGraphServer()`。

**实现思路**：

- 复用 `src/server/host.ts`、`src/server/app.ts` 和现有 Runtime。新增薄 CLI 入口，命令建议为 `pnpm start`；若提供 `pnpm dev`，前后端同源/代理关系应明确。
- 支持显式配置路径、stateDir、loopback 端口。默认数据目录与当前 cwd 解耦，输出规范化后的实际目录及 URL。
- 缺少配置时进入可理解的首次运行/待配置状态，不能崩溃，也不能假装模型可用。为 T05 留入口。
- 区分仅查看与启用任务调度；参数和页面清楚显示当前模式。浏览历史数据不得隐式启动收费请求。执行模式下仍沿用任务确认、权限、预算和恢复规则。
- 正式启动应检查 Web 构建是否存在；不存在时给准确构建指令，不能成功启动却只显示默认占位 HTML。
- 本阶段支持终端前台后台宿主，浏览器可独立关闭。不要求自动安装 launchd 或桌面安装包。

**验收标准**：

- [ ] 干净临时配置下，按文档命令即可打开真实 React 页面；访问地址实际可用。
- [ ] 重启及从不同 cwd 启动仍指向同一显式数据目录，任务列表保留。
- [ ] 同一数据目录第二后台被已有所有者机制阻止，不重复派发。
- [ ] 端口占用、配置不存在、Web 构建缺失分别有明确错误与非成功退出/状态。
- [ ] 关闭浏览器不停止测试任务；重新打开能看到进度。仅查看模式零派发。
- [ ] SIGINT/SIGTERM 的停止行为有界且明确；存在在途调用时不把强制终止记作成功，重启沿用核查机制。
- [ ] 只绑定 loopback；自动化浏览器测试不需要真实供应商凭据。

## T02 · 持久配置与模型/凭据绑定

**任务说明**：提供一个受后台控制的配置来源，为多个项目、多个模型和多个凭据建立稳定身份，替换“所有模型共用一个全局 apiKey”的限制。

**实现思路**：

- 先定义最小配置 schema 与版本：项目、模型（provider/baseURL/model ID/等级/偏好）、credentialId、可选 sharedLimitGroupId、并发限制。具体模型 API 类型必须属于已验证 transport，不能仅靠名字认为兼容。
- 第一版可采用非秘密配置文件加环境变量/受控秘密存储引用。建议 credential 保存 `secretRef`，例如环境变量名；不要求为此引入新的云秘密服务。
- 后台解析明文秘密；前端仅接收凭据 ID、显示名、引用和是否已配置。不得把真实 key 写入 API 响应、SSE、日志、错误或导出的配置。
- 配置写入经 Runtime/配置服务验证，不让 Web 直接写正式数据库。使用原子保存与配置版本检查，失败不破坏旧配置。
- 明确变更生效时点。第一版可要求相关任务停稳后重载；不要求任意热更新。模型、定义、凭据的运行绑定可追踪，不能悄悄改写执行中实例。
- 同一供应商实际凭据被多个别名引用时，也不能绕开同一限制。使用后台内部规范化身份，或强制它们归属同一共享组；不用明文 key 充当 UI ID。
- 旧单 key 编程入口保留兼容映射，或提供明确迁移及可回退路径，避免破坏既有 harness 与测试。

**验收标准**：

- [ ] 两个本地模型端点分别收到各自正确的合成凭据；一个模型切换到另一凭据不会串 key。
- [ ] 重启后项目、模型、凭据引用及偏好保持；空凭据/无效模型引用在派发前明确拒绝。
- [ ] 写入非法配置不损坏旧版本；并发编辑有版本冲突提示，不静默覆盖。
- [ ] 执行中修改相关绑定受到既定生效规则约束，历史记录仍指向原配置版本。
- [ ] 设置查询、任务详情、SSE、错误与配置导出中均不出现合成秘密原文。
- [ ] 现有单 key 用例和 A13 harness 的配置接口兼容性得到验证。

## T04 · 按凭据及共享组限制 API 并发

**任务说明**：限制每个凭据当前实际在途模型请求数量；多个模型/Agent 共用同一凭据时共享限制，达到上限排队。

**实现思路**：

- 在受控 provider 实际发送路径统一接入名额机制，覆盖主管、工人、审查、压缩/摘要与合法重试。不要只包最外层 Agent 会话。
- 限制范围是后台共同管理的凭据/共享组，不是每实例各维护一个计数器。凭据上限与共享组上限同时存在时都须满足；没有共享组的独立凭据互不阻塞。
- 不在等待名额时占用数据库写事务。排队获得名额后、实际发送前，重新校验暂停、权限、预算、任务代次和配置有效性。
- 名额覆盖完整请求生命周期：收到响应头不代表结束；SSE 结束/出错/取消并完成本地传输清理后才释放。未知 usage 仍走原核对规则，名额与用量不能混为一笔账。
- 排队期间不产生“已实际发送”的 invocation，不虚增已用 token。预留额度与 Agent 执行名额的占用策略必须明确，等待释放/恢复规则与现有调度保持一致。
- 队列可取消并避免饥饿；等待凭据 A 不阻塞使用凭据 B 的独立可运行分支。
- 进程重启不能把旧计数原样锁死，也不能不经在途核查就把所有旧请求视作已结束。明确进程所有权、旧 worker 核查与额度恢复顺序。
- 第一版只做并发，不将 RPM/TPM、429 计费或自动切 key 混入实现。新增限制的默认值及范围在配置文档说明。

**验收标准**：

- [ ] 本地延迟/流式 provider 记录真实在途数：同 key 两个模型、至少三个实例，配置上限 2 时始终 ≤2。
- [ ] 不同 key 独立运行；不同 key 同属一个上限 2 的共享组时合计始终 ≤2；凭据别名不能绕过限制。
- [ ] provider 发出响应头后持续阻塞响应体，名额不能提前释放。
- [ ] 成功、传输失败、用户取消均正确释放名额；未知 usage 保留未知与对应阻塞，不折为零。
- [ ] 排队后暂停任务或改变有效配置，出队时不得绕过门实际发送；恢复后仍正确排队并且不重复计费。
- [ ] 排队不持有长写事务，不阻止用户查询/答复，不阻止独立凭据分支继续。
- [ ] 重试重新申请名额并重过门；测试覆盖主管及至少一条辅助模型调用路径。
- [ ] 运行中降低上限不强杀已有请求，但新请求等待到符合新上限；若第一版只允许停稳修改，应验证明确拒绝运行中改动。
- [ ] 后台重启后队列/名额可恢复，无永久占用、重复派发或恢复瞬间超限。

**验收标准**：

- [ ] 所有必需 T01–T07 条目有通过证据或明确未完成记录，不用“基本完成”掩盖缺项。
- [ ] 项目正式 Node 版本下，相关回归、完整 Vitest、双 tsc、Web build、diff check 通过。
- [ ] 原 R6、S4、R8–R13 的探针保持正确；依赖/执行沙箱变更时补真实 Chromium 交付 E2E。
- [ ] 真实浏览器完整流程通过，提供关键页面截图及原始测试结果；截图不能替代行为断言。
- [ ] 失败/重启测试有外部截止时间，能清理自己创建的进程；等待命令定期返回状态，不遗留孤儿。
- [ ] 报告包含准确提交、变更范围、测试命令/次数/结果、未知与未验证边界、工作区残差。
- [ ] 最后交独立验收 agent 按 Standards / Spec 复核；实现 agent 只报告完成情况，不代替独立验收宣布通过。

## T09 · RPM/TPM 与 429 冷却（后续可选）

**任务说明**：在并发控制稳定后，补供应商按分钟请求/token 配额和限流响应处理。

**实现思路**：按 provider/账户/共享组建速率策略；处理 Retry-After；输入/输出预估与实际统计关系清楚；重试沿用现有安全重试与未知 usage 规则，不假设所有 429 都是零消耗。

**验收标准**：

- [ ] 可控时钟与 provider 证明请求速率、token 配额和冷却有效，恢复不造成集中突发。
- [ ] 429/缺失 Retry-After/暂停时冷却等场景可复现；不绕开预算门，不重复计量，不自动轮换 key 规避共享配额。
- [ ] 用户能看到限流原因与下一次可尝试时间。该任务未完成不影响仅承诺并发控制的 T04 验收。

## T10 · 开源项目定向借鉴（后续可选）

**任务说明**：围绕 Graph 的具体体验缺口给出小范围可实施建议，不进行框架替换竞赛。

**实现思路**：优先考察 Open SWE 的交付闭环、OpenHands 的控制台、Vibe Kanban 的工作区/审查交互，以及 LangGraph / Microsoft Agent Framework 的观测与恢复接口。开始任务时重新核对仓库当前状态、许可证和维护情况，固定参考提交；Vibe Kanban 在本轮调查时已公告 sunsetting，应作为参考而非默认依赖。

**验收标准**：

- [ ] 产出对照表：Graph 具体问题、参考实现链接/提交、适用设计、预计改动和不采用的原因。
- [ ] 最多提出三个可独立实施的改进，每项附验收方式；不把“引入 LangGraph”当默认结论。
- [ ] 只提交调研与建议，不未经新任务确认直接搬入代码或替换核心依赖。

## 实现 agent 的交付格式

每个任务报告至少包含：

1. 任务 ID、起始提交、完成提交与实际修改范围。
2. 本文验收清单逐条状态，附可复跑命令和证据路径；失败结果也要保留。
3. 新增接口、配置 schema、生效/迁移规则；没有变更的写“不涉及”。
4. 相关测试与全量测试分别运行了几次，在哪个提交；不要把旧输出改标签当成新复验。
5. 运行目录、遗留进程/文件检查、未完成项与已知限制。
6. 需要独立验收重点挑战的边界，以及是否运行过真实供应商调用和实际用量。

使用者将完成报告交回独立验收 agent 后，再作验收与改进建议。除非任务明确要求，不修改原 MediaBookmarks 仓库、不重写历史任务数据库、不发布外部消息、不合入远端或发布产品。固定范围内的普通实现选择由执行 agent 自行推进；涉及扩大权限、改动验收标准或新的真实付费运行，按既有用户授权与项目协议处理。
