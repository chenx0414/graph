## Generic fallback reachability proof

capabilityConfigView's successful branch computes configured from the same collected fields, missing as their complement, and ready = missing.length === 0. Therefore ready=false implies missing.length>0. Its catch branch always adds error, obtained from real read/parse errors with a message. capabilityConfigViews additionally removes results with no fields and falsy error. No HTTP input accepts ready DTOs: GET /api/settings derives them from catalog files/current secret values; settings is fetched by the UI, not client supplied.

For a list row, guidance is rendered only in the unconfigured group. Invalid status immediately takes capabilityConfigGuidance's manifest-error branch. Available status with no config is considered configured and never renders guidance. Available status with a producer-created unready config either has nonempty missing (specific instruction) or an error (error instruction). The config panel likewise renders guidance only for unconfigured; successful no-field manifests are filtered out, and readable configurations with zero missing are configured. Thus the generic instruction remains defensive code but the old synthetic no-detail example has no current end-to-end producer.

Native skills with only SKILL.md do not invalidate this reasoning: config builder attempts capability.json because native snapshots have no manifest; failed read yields an error DTO, not false/empty/noerror. Duplicate records marked invalid may have a readable source; list still takes invalid-status guidance, and successful no-field config is omitted. An arbitrary internal exception with empty string could make error falsy, but then fields empty causes capabilityConfigViews to filter it out. This is not a credible public path to generic guidance.
