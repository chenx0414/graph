## Why B4's exact state is not a normal public reservation contract

- `reserveNodeTokens` has one production caller: `NodeExecutor.runOne` (around185). It is not exposed by supervisor/user graph APIs.
- `GraphRunner.drain` (around142) owns an active Map keyed by node ID and skips nodes already active. `NodeQueue.claim` (around90) refuses another claim while any row for that node is claimed. A queued second input cannot reserve during the first in-flight execution.
- Within one execution, executor's ordinary known-usage path calls releaseHold before success/error/retry/resubmit continuation (around260); retries cannot preserve the old finite hold and reserve again on that ordinary path.
- Unknown real provider sends do preserve a hold, but NodeExecutor's entry guard (around150) refuses a finite execution when kernel_provider_calls contains unknown. The real last unlimited workflow proves restart/quota/retry does not reach a second vendor send or alter that hold.
- Startup recovery (kernel-recovery) first makes inflight calls unknown. If no unresolved call exists it releases the old token_reservation before any resumed turn. If unresolved usage exists, it preserves the hold and parks the node, and the above finite unknown guard applies.
- Explicit reconcile_usage is public graph-service→reconcileKernelUsage; it clears the aggregate hold only when no pending call or running execution remains. Then retry may reserve afresh.
- Provider-level gate itself checks used+inflight/unknown provider reservations before inserting its call. Those are a different ledger boundary than manually calling reserveNodeTokens twice; do not conflate the two.

Thus dropping B4 does not drop proof of an independently supported public operation permitting parallel same-node execution reservations. Its meaningful public effects—refusal without extra send/charge/hold pollution, and preservation of a real unresolved hold—are exercised by the native keepers. This is source-based current-path reasoning, not a claim that arbitrary internal/manual SQL states are impossible.
