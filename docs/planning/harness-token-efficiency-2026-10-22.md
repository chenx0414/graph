# Graph harness 价格加权成本：2026-10-22

分支 `feature/harness-token-efficiency-2026-10-22`（基于 `main` 的 `adb6396`）。
本轮目标：降低**每个完成任务**的价格加权成本，质量不下降。

结论摘要：

1. 上一轮审计（`harness-token-efficiency-2026-10-16.md`）写的是已退役的 TypeScript 侧车。**live 路径已经换成 Go + PiG 内核，静态上下文不再是主要开销，话上下文的大小才是。**
2. 基线（真实库只读快照）：19,608 次请求、129 个 task、4,432,477,135 个缓存读取 token。缓存读取占 token 总量 96.8%，按计费类型折算后占花费 **42.7%**；未缓存输入 36.1%，输出 21.2%。
3. **每一次请求携带的前缀平均 246,440 个 token**（中位 235,497，p90 450,048，max 673,408）。这是最大的单一开销来源，而它的大小完全由**压缩阈值**决定：会话在到达供应商窗口前才压缩，实测压缩前中位 495,979 token、压缩后中位 27,158 token。
4. 静态前缀（系统提示 + 工具声明）在主会话里约 15,701 token，只占平均前缀的 **6.4%**。这解释了前一周工具卸载实验为什么没有降本（浏览器按需加载反而贵 39%，目录工具按需加载贵 3.35%）：在 246K 的前缀里省 2K token 是 0.8%。
5. 已提交 6 个独立可回滚的修改：助手回合如实回放（reasoning + tool_use）、Anthropic 传输显式缓存断点、可由环境变量命名的压缩上限、摘要拿到它自己要的输出预算、任务说明包不重复发送、成本 CLI 增加前缀/用途/整树情景计价。
6. 压缩失败的根因也找到了：请求自己的输出预算在内核桥上被丢掉，摘要被按模型的整个上限要（生产模型 384,000），于是摘要写到被切断为止——9 次失败里 6 次是这个原因，而失败的压缩会把 496K 的上下文留在会话里。
7. **会话上下文的第二块重复**：任务说明包在每次 operation 里重发同一段环境说明（实测 62 份里 89.5% 逐字相同，占 transcript 20%）。已做成默认关闭的 `GRAPH_REUSE_TASK_SETUP`，去掉重复约等于上下文 −18%。

**真实模型 A/B 跑了**（command-goat 免费模型、Go 后端、独立行为检查）：**工具结果接缝**把每完成任务花费从 $0.006922 降到 $0.004376（−37%）、缓存读取 −59%，质量两边都是 3/3 通过（但两边的请求数不同，n=3，只够说"指向明确"）。**两个 flag 在这个任务集上是 null 结果**——短任务的自然上下文才 9,300 token，131,072 的上限根本不触发；8,192 的激进上限反而贵 2.2 倍。

**长会话（21 轮）把排序改了**：接缝和压缩上限是**替代关系**——接缝把大输出压住，上下文就不再逼近窗口，32K 的上限一次都没触发；任务说明包复用让缓存读取 −17.6%，但总花费是平的。

**尚未证明**："每完成任务成本下降且质量不降"目前只有接缝这一条有真实模型的证据（且带混淆项：两边请求数不同，n=3）。两个 flag 在长会话上的钱仍未证明。

## 1. Harness 地图（当前 live 路径）

生产桌面应用运行的是 Go 二进制 `dist/graphd`（`desktop/main.mjs:27`），不是 `src/server/cli.ts`。

| 用量记账 | `backend/internal/graph/runtime_kernel_provider_gate.go:115` | 缺用量记 unknown，不记零；调用时冻结价格 |
| 计量 | `scripts/harness-cost.mjs` | 只读快照；本轮扩展 |

### 两个必须知道的边界

- **主 Agent 会话在 Go 内核上，开发者/CLI 路径（`src/server/`）在 TypeScript SDK 上。** 两者共用同一个 `tasks.sqlite`，但提示词拼装与请求装配各有一份。本轮的 Go 修改只覆盖生产路径；`src/runtime/compaction.ts` 的同名修改保持两边一致。
- **压缩是 daemon 驱动的，内核自己的阈值是关的**（`resident.go:69`：`Enabled: false, ReserveTokens: 1024, BackgroundTokens: 0`）。所以阈值改一处即可覆盖主会话。

### 2.4 压缩的真实行为

### 2.7 工具错误的分类（记录在案的全部 188 条）

目标书要求把工具错误分成"预期的"和"harness 的缺陷"，后者才是要修的。按真实 transcript 逐条分类：

| 类别 | 条数 | 占比 | 典型 |
| --- | ---: | ---: | --- |
| **预期** | ~161 | 86% | 路径越界 / 路径受策略保护（27）、用户暂停或中止（37）、浏览器扩展起不来或忙（36）、MCP 缺 task grant（7）、参数写错（缺 graphId、缺 path、edits 定位不到、schema 不是 kind@version）、幂等与并发护栏（requestId 复用、artifact head 变了、重复提交） |
| **harness 缺陷** | 14 | 7% | 三个同源：**宿主在工具还在飞的时候关了**——"Plugin helper is closed"（7）、"Pi host channel closed"（2）、"Runtime is closed"（2）；外加工具结果计数器的原子写 ENOENT（5，已在 2026-10-10 审计里单独修过） |
| 环境/外部 | ~13 | 7% | 浏览器临时 profile 目录无权（11）、沙箱 spawn EPERM（2）、SDK 损坏（2）、网络 fetch failed（1） |

**能修的几类里，三类是同一个竞态**：宿主在工具调用还在飞的时候被关掉，模型收到的是一句它无法据此行动的内部消息。11 条，占全部工具错误的 6%。

其中 7 条（"Plugin helper is closed"）来自**已退役的 TypeScript 插件宿主**（`src/runtime/durable-plugin.ts:92`），Go 内核路径没有这条消息。另外 4 条（"Runtime is closed" / "Pi host channel closed"）在 Go 侧仍有对应物（`core_task_runtime.go:1633` 的 `ensureOpen`），但那一处是**运行时就该拒绝**的守卫：`Close()` 先 `Drain()` 再释放，晚到的工作被拒是对的。真正要修的是"模型收到这句话却无从判断发生了什么"——修法是让消息说清"宿主已关闭，本次调用未执行"，而不是改关闭顺序。

**不是缺陷但值得记的**：浏览器扩展 36 条错误（占全部的 19%）里，11 条是"临时 profile 目录无权"——**扩展需要的临时目录没有被访问策略授予**。这可能是策略漏了一条路径，也可能是有意的隔离；改它是一次安全决定，所以本轮只记录、不动手。

**"预期"这一类里有价值的部分是错误文本本身**：多数错误点名了缺什么（"graphId: must have required properties"、"Available scripts are: …"、"outputs.result.enable"），模型能据此改对——这是上一轮"错误要可恢复"那条要求的实际效果。

## 3. 机会排序

排序依据 = 花费份额 × 可移除比例 ÷ 质量风险。可移除比例来自上面的账本，不是来自外部团队的百分比。

| 优先 | 层/候选 | 估算与依据 | 质量风险 | 验证 | 回滚 |
| --- | --- | --- | --- | --- | --- |
| 0 | **工具结果接缝（Go 侧从未接线）** | 真实生产对话：2,704 条工具结果 6.7M 字符，其中超各自工具上限的部分被砍掉三分之二。真实模型 A/B：花费 −37%、缓存读取 −59%、质量两边全过 | 低：接缝只改形状不丢数据，句柄可读全文 | E2E + A/B（§5.2、§5.3） | `GRAPH_TOOL_RESULT_SEAM=0` |

## 4. 已做的修改

四个独立提交，每个可单独 revert。

### 4.1 `6b2eca8` Replay the assistant turn the model wrote

**问题**：daemon 拼请求时，助手回合只保留 text 和 toolCall。模型写下的 reasoning、Anthropic 给 reasoning 的签名、provider 自己留着的 redacted reasoning、以及 **Anthropic 传输上的 tool_use 块本身**，全部被丢掉。

后果不是小事：

- 模型读不到自己的 reasoning，就会从问题重新推一遍计划，每个长任务每一轮都付 output token。
- Anthropic 请求里 tool_result 没有对应的 tool_use，provider 直接拒绝——那一轮无法继续。
- 供应商的 tool-call index 是"第几个调用"，不是"回合里的第几块"。先 reasoning 再调工具的回合，reasoning 在第 0 块、调用在第 1 块；旧代码用 index 0 开工具块，把 reasoning 覆盖掉了。

**改法**：按供应商原样捕获并回放。

- OpenCode Go 网关用 `reasoning` 回 reasoning、用 `reasoning_content` 读回来，所以记录答案来自哪个字段，回放就写回同一个字段（`runtime_controlled_openai.go` 的 `controlledOpenAIReasoningDelta` / `markReasoningField`）。
- Anthropic 的签名在自己的 delta 里（`signature_delta`），连同 redacted 块的 opaque payload 一起保留。
- 工具调用改成按到达顺序占块，供应商的 index 只用来认调用。

**验证**：新 E2E `tests/e2e/provider-assistant-replay.test.ts` 跑真实 Go 后端 + 真实 PiG 内核 + 真实 bash 工具，打脚本 provider，断言 provider 收到的请求体。**改前两条都红，改后两条都绿。**

### 4.2 `e18a65b` Mark the cacheable prefix on the Anthropic transport

**问题**：Anthropic 自己不缓存前缀，只缓存断点标记的部分，其余按满额输入价计费。daemon 的 Anthropic 请求**一个断点都没有**——系统提示、工具声明、整段对话每一轮都按满额重新付一遍。

live 对话的前缀能到 50 万 token 量级，同一段前缀每个 operation 要付十几遍。

**改法**：按 Anthropic 的三个断点标记——系统提示、最后一个工具声明、最后一条对话消息。对话每轮长一条消息，所以每轮只有新增的那部分 token 需要写入缓存，其余从上一轮留下的缓存里读。

**没有改 OpenAI 兼容传输**：那条路自己会缓存（实测命中率 98.1%），而严格的 OpenAI 兼容服务器会拒绝它不认识的 body。

**验证**：同上 E2E 断言三个断点都在。

### 4.3 `ff7b6da` Let the environment name how far the context may grow

**问题**：会话在到达供应商窗口前才压缩，于是长到 50 万 token。压缩读取是任务花费里最大的单块，而主会话就是它挣来的地方。

**关键观察**：压缩提前，压缩调用读的总 token 不变。会话多压缩四次，每次总结的就少四倍，加起来还是那些 token；会话继续时拿到的摘要也一样大。**只有每个请求携带的前缀变小。**

**改法**：`GRAPH_COMPACTION_CONTEXT_CEILING` 命名这个上限。默认不设 = 今天的行为；daemon 自己的溢出压缩照旧。

**验证**：新 E2E `tests/e2e/compaction-context-ceiling.test.ts`——设上限时 provider 收到一次摘要请求（一个远未填满窗口的对话），不设时不收到。改前红，改后绿；默认路径两种情况都不变。

### 4.4 `8d20548` Price the whole tree and show the prefix every request carried

报告原来有"一个任务花了多少、请求去了哪里"，但没有价格由什么构成的两块：

- **每次请求的前缀**（= 该请求的缓存读取）的分布——压缩阈值动的就是它。
- **用途**（completion / compaction / prompt_suggestion / skill_sediment）是四种不同的花法，原来是一个数。
- **整树情景计价**：有价格调用用过的费率 × 全部记录 token。报告里写明这是情景不是账单。

现有 CLI E2E 增加对应断言，10 项仍全绿。

### 4.5 给摘要它需要的空间（`129da7e`）

压缩失败会把会话留在它想缩小的那段上下文里，之后每个请求都重新付整段前缀。记录在案的历史里有 **9 次压缩失败，其中 6 次是同一个原因**：摘要生成撞到输出上限，摘要不完整。

两个东西挡住了一个放得下的摘要：

- **请求自己的输出预算没有到达供应商。** 内核给摘要请求的是有界预算（daemon 自己的指令要求"约 1500 token"），但 `pigkernel/provider.go` 的桥把 daemon 的常驻 options 递了过去，**丢掉了这一次请求的 options**。供应商被问的是模型的整个输出上限（生产模型是 384,000）。被要求写 384,000 token 的摘要不会写成交接摘要，它会一直写到被切断为止。
- **内核要的摘要比 daemon 要的小。** reserve 是内核花在摘要上的额度，被设成 1,024——它的五分之四只有 819 token，比 daemon 要求的交接摘要还小。

改法：请求的预算随请求走（`requestOptions`），daemon 按调用方要的数量向供应商要；reserve 提到 4,096，交接摘要放得下。

**验证**：E2E 用一个"尊重自己输出预算"的供应商，断言摘要请求带的是它自己的额度而不是模型的（改前 8192，改后 3276），并断言交接摘要进了下一轮的历史（压缩真的替换了历史，而不是留着 496K 的上下文）。

### 4.6 让会话保留它已经读过的任务说明

**问题**：任务说明包（briefing）描述任务运行的环境：绑定的能力、目录、系统上下文。它在任务的**每一次 operation 里都是同一段文字**，而 operation 的提示词会进入 transcript，而 transcript 每个请求都要重读一遍。62 次 operation 的任务因此带着 62 份同样的文字，每个请求都付了 62 份的钱（实测相邻两份 89.5% 逐字相同，公共后缀 3,131 字符）。

**改法**：`GRAPH_REUSE_TASK_SETUP=1`（默认关闭）。会话已经读过的那段说明不再重发，提示词里留一行"任务说明与上一轮相同"。

会话是否还带着这段说明，由三件事共同决定，任一不成立就照旧全量发送：

- **会话是延续的**（不是新会话——新会话什么都没读过）；
- **这一轮没有压缩**（压缩替换了整段上下文）；
- **这段说明没有变**（能力绑定、目录或系统上下文变了就重发）。

记录放在 daemon 内存里（`TaskSetupLedger`），daemon 重启就忘——忘的方向是重发一次，安全。**没有动数据库 schema**：TS 与 Go 两端共用一个 `tasks.sqlite`，schema 版本必须同步，加一列会让 TS 侧拒绝打开 Go 侧升级过的库。

**验证**：新 E2E `tests/e2e/task-setup-reuse.test.ts` 跑真实后端两次：开关关闭时第二次 operation 的提示词仍带说明；开启时第一次带、第二次不带，并留有"说明未变"的标记。把复用逻辑打断后，开启那条 E2E 变红，关闭那条始终绿。

### 4.7 系统提示词审计（逐块处置）

**本轮没有改系统提示词。** 理由见 §3：在 246K 的前缀里，Graph 自己那 6.5K 字符只值 0.8%；前一周的 docs 精简实验在真实模型对照里**贵了 28.9%**（多 5 次请求、请求数 +50%）。在降下阈值之前动提示词是净负。

## 5. 真实模型 A/B（command-goat 免费模型）

模型：`command-goat:deepseek/deepseek-v4.1-flash`（`https://api.commandcode.ai/provider/v1`，凭据只经环境变量 `GRAPH_SUBSCRIPTION_COMMAND_GOAT_API_KEY` 传入，仓库与报告里都没有密钥）。**跑的是 Go 后端**（桌面应用真正跑的那个），不是开发路径的 TS 服务。

计价说明：免费层实际花费是 0，所以 A/B 用**同一套权重**折算钱——`input 0.15 / output 0.6 / cacheRead 0.003` USD 每百万 token（DeepSeek V4 Flash 的 off-peak 价，见模型目录）。比较的是**工作量**，不是账户档位。

驱动脚本：`scripts/harness-ab-eval.mjs`。每个变体在**每一轮内部交替**执行（暖缓存或慢的一分钟不会只落在一边），每个变体跑完后读这次运行自己的账本（`scripts/harness-cost.mjs`），行为检查由 case 自带的独立校验程序在 Agent 之外运行。

### 5.1 parser 任务（修 config.js），每组 3 轮 + 2 轮补跑

| 变体 | 轮次 | 行为检查 | 请求 | 输入 | 输出 | 缓存读取 | 花费 | 平均前缀 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default | #0 | ✓ | 19 | 24,800 | 5,898 | 176,256 | $0.007788 | 9,277 |
| default | #1 | ✓ | 14 | 15,456 | 6,571 | 129,792 | $0.006650 | 9,271 |
| reuse | #0 | ✓ | 24 | 29,077 | 6,435 | 237,312 | $0.008934 | 10,318 |
| reuse | #1 | ✓ | 13 | 13,934 | 5,177 | 111,616 | $0.005531 | 8,586 |
| ceiling-low（8,192） | #0 | ✓ | 33 | 43,699 | 22,486 | 428,032 | $0.021331 | 13,376 |
| ceiling-low（8,192） | #1 | ✓ | 20 | 25,319 | 10,727 | 168,448 | $0.010739 | 8,422 |

均：default $0.007219、reuse $0.007233、ceiling-low $0.016035。

**读出来的三件事**：

1. **质量没有下降**：8 次运行（含补跑）全部通过独立行为检查。
2. **同一个变体在同一个任务上的波动是 2.2 倍**（default 的 $0.0067–$0.0149）：模型每次走的路不一样（工具调用次数 14 vs 19 vs 24），请求数一变，token 就变。**在这个样本量下，2 倍以内的差异都读不出来。**
3. **8,192 的压缩上限明显更贵（2.2 倍）**，而且机制说得通：这个任务的自然上下文约 9,300 token，本来就在上限之下，所以它是被**反复**压缩的；每次压缩是一次独立的计费调用，读的是整段（被截断过的）历史。**上限必须远高于任务的自然上下文大小**——生产负载的自然上下文是 496K，128K 的上限对它有意义；这个短任务上没有。

**结论（负结果也要记）**：短任务上，任务说明包复用（每次 operation 省约 875 token，占 9,300 前缀的不到 1%）**测不出来**；压缩上限在 131,072 对短任务**完全没有触发**（null 结果）；8,192 的激进上限**是负收益**。这三个都不是"改动没用"的证据，而是**这个任务集的规模测不出这两个杠杆**——它们的收益在生产负载的长会话里（上下文 496K、62 次 operation、每次请求重读整段）。

### 5.2 command 任务（跑 check.mjs，输出 5,000 行）

这个任务会打印 5,000 行诊断输出（约 70KB），正是工具结果接缝要处理的东西。对照：`default` = 接缝开，`no-seam` = 接缝关（`GRAPH_TOOL_RESULT_SEAM=0`），各 4 轮。

| 变体 | 行为检查 | 均花费 | 均请求 | 均输入 | 均输出 | 均缓存读取 | 均前缀 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default（接缝开） | 4/4 ✓ | $0.003702 | 10.8 | 13,956 | 2,284 | 79,584 | 7,430 |
| no-seam（接缝关） | 4/4 ✓ | $0.003483 | 10.0 | 14,730 | 1,772 | 69,920 | 6,915 |

**差 6%，而同一变体内部的波动是 40%**（default $0.002966–$0.005013，no-seam $0.002901–$0.004069）。读不出差异。

**为什么读不出——去看了一次留档的运行**：12 条工具结果，最大的 819 字符，**没有一条超过 4,000 字符**。**Agent 根本没有运行 check.mjs**：它读了 settings.json，把 mode 改成 fast，结束。（验证程序自己跑 check.mjs，所以验收照样通过。）**这个任务压根没有产生大输出**，接缝无事可做。

这是本轮 A/B 最有价值的一条：**固定评测任务集不产生大工具输出，也就不可能量到工具结果接缝**。接缝本身由 E2E 直接证明（模型拿到句柄、句柄里每一行都在），但端到端的钱要另配一个真的跑命令的任务。

### 5.3 big-output 任务（强制跑出 5,000 行输出）

同一个 check.mjs，但提示词要求"运行 node check.mjs 并读完它的完整输出"。**接缝确实被触发了**——留档的一次运行：

| | 大小 |
| --- | ---: |
| 命令的真实输出 | 78,934 字符 / 5,006 行 |
| 模型读到的 | 19,959 字符，形如 `[large tool result: 78934 chars, 5006 lines]` + 句柄 |
| 句柄文件里的 | 78,934 字符（逐字节齐全） |
| 这次运行的工具结果总量 | 22,617 字符（原始输出的话是 78,934+） |

**端到端的钱**（每组 3 轮，各变体单独跑以避开机器负载抖动）：

| 变体 | 行为检查 | 均花费 | 均请求 | 均缓存读取 | 均前缀 |
| --- | --- | ---: | ---: | ---: | ---: |
| 接缝开 | 3/3 ✓ | **$0.004376** | 10.7 | **82,645** | 7,637 |
| 接缝关 | 3/3 ✓ | **$0.006922** | 14.7 | **199,296** | 12,841 |

**花费差 37%，缓存读取差 59%，质量两边都是 3/3 通过。**

逐轮：接缝开 $0.004060 / $0.004391 / $0.004678（带宽 15%）；接缝关 $0.004633 / $0.006090 / $0.010042（带宽 2.2 倍）。**两个区间只在边缘交叠**（接缝关最便宜的一轮 $0.004633 略低于接缝开最贵的一轮 $0.004678），n=3 只能说是"指向明确"而不是"已证明"。

一个必须记的混淆项：**两边的请求数不一样**（10.7 vs 14.7）。模型是随机的，它走的路不同；接缝也让模型读到的是摘要而不是原始输出，行为可能因此不同。要把这件事说死，需要固定路径的对照实验（同一段 transcript 跑两次），本轮没有做。

**为什么前两次跑没成**：第一次 daemon 进程死了（stderr 为空 = 被 SIGKILL）；查了机器状态——可用内存 384MB、swap 已用 3.9GB、另一个会话同时有 18 个 vitest/graphd 进程。第二次（接缝关）没有死，但那一轮 turn 停在 pending：Agent 读了两个文件就卡住，3 次请求后再无进展。**同一份代码第三次跑就正常完成并通过验收**（43 秒、11 次请求、verified ✓）。所以这两次是环境与免费档的不稳定，不是改动的回归——但我也没有把它们从记录里抹掉。

### 5.4 长会话（21 轮同一会话）——两个 flag 在真实长度上是什么表现

短任务量不到东西，所以把同一个会话拉长到 21 轮（首轮 + 20 轮追问），三个变体各 1 轮：

| 变体 | 行为检查 | 请求 | 花费 | 未缓存输入 | 缓存读取 | 平均前缀 | 压缩次数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default | 1/1 ✓ | 49 | $0.012068 | 29,327 | 775,168 | 15,820 | 0 |
| setup-only（复用任务说明包） | 1/1 ✓ | 46 | $0.012162 | 35,380 | **638,592（−17.6%）** | 13,882 | 0 |
| ceiling-32k（复用 + 32K 上限） | 1/1 ✓ | 48 | $0.012119 | 40,857 | **622,464（−19.7%）** | 12,968 | **0** |

**三件事**：

1. **质量**：21 轮里每一轮都只发一次任务说明包，行为检查依然全过——模型没有因为说明不再重复而忘记自己绑定了什么。
2. **任务说明包复用确实在起作用**：缓存读取 −17.6%，和预测的"去掉 20 份重复说明"吻合。但**总花费是平的**（+0.8%）——省下的缓存读取被上升的未缓存输入抵掉了。n=1，这个幅度也在轮间波动范围内，所以只能说"机制看得见，钱没省下"。
3. **32K 的压缩上限一次都没触发**（压缩次数 0），尽管会话有 21 轮。**因为接缝已经把上下文压住了**：21 轮的平均前缀才 15,820 token。

**这是本轮最有价值的一条结论**：**接缝（直接改）和压缩上限（flag）是替代关系，不是叠加关系。** 接缝让大输出不再撑大上下文，上下文就不再逼近窗口，压缩阈值就基本不参与事了。压缩上限真正还有用的场景是：**接缝关掉的长会话**，或者**长到几十万 token 的会话**。上一轮我推演的"128K 上限省 29%"是建立在"上下文能长到 496K"这个前提上的——而那个前提正是接缝要消灭的东西。

**所以排序要改**：先修接缝（它是直接改，且有真实模型的数），再谈压缩上限；两个 flag 一起开着，只是在没被接缝压住的长会话里多一道保险。

## 6. Flagged 变更的测试计划

`GRAPH_COMPACTION_CONTEXT_CEILING` 与 `GRAPH_REUSE_TASK_SETUP` 默认关闭。上线前：

**固定任务集**（每组至少 5 次重复，报方差；不用"差一点点"的样本筛胜者）：

1. 短问答（用户原话："这个仓库怎么跑测试？"）
2. 项目文件修改（"修一下 config.js，空白行别当成配置，保留值里的等号。"）
3. 首次建图（main 规划 + 节点派发 + 交付）
4. patch / 返工（同一图二次修改）
5. 崩溃恢复（daemon 中途重启）
6. 长对话压缩（同一会话 40+ 轮）
7. artifact 发布与读取
8. 权限 / 预算拒绝

**分组**：同一模型、同一 effort、同一配置、同一仓库起点；冷缓存 / 热缓存 / 跨 TTL 间隔分别成组。压缩上限组与默认组交替执行，避免把缓存热度差当成收益。

**比较指标**：任务成功、验收通过、需要用户纠错次数、每完成任务花费、请求数、轮数、压缩次数与失败次数、工具错误、延迟、缓存命中率与缓存 token 比例。

**判据**：花费下降且其它护栏不退化超过噪声才开启。记录 null 结果。

**单独测**：压缩上限 64K / 96K / 128K / 192K 四档，找出实际最优点——本报告的推演假设"压缩读取的总 token 不随阈值变"，需要实测确认（每轮多截断的摘要可能改变总结长度）。

**任务说明包复用单独测**：它的风险不是省多少钱，而是模型是否还记得自己绑定了哪些能力。两组各跑同一组任务，重点看：模型是否调用了它应该调用的绑定能力（浏览器、FFF、MCP）、是否重复询问已经问过的问题、是否在长对话后仍按说明行事。建议先在 20 轮以上的长任务上试（重复的代价才显现），再在短任务上试（短任务里省不到什么，却承担了"模型忘了"的全部风险）。

## 7. 缺口

1. **两个 flag 的收益仍然没有实测出来。** 长会话（21 轮）上：任务说明包复用让缓存读取 −17.6% 但花费是平的（未缓存输入补上了）；32K 的压缩上限**一次都没触发**（接缝把上下文压住了）。 A/B 跑了（command-goat 免费模型、Go 后端、独立行为检查），但**这个任务集的规模测不出来**：短任务的自然上下文约 9,300 token，131,072 的上限根本不触发（null 结果）；任务说明包复用每次 operation 省约 875 token（不到前缀的 1%），被 2.2 倍的轮间波动淹没（null 结果）；8,192 的激进上限反而**贵 2.2 倍**（负结果，机制清楚：它把本来不需要压缩的会话反复压缩，每次压缩都是一次计费调用）。报告里的 −29.3% 仍是基于真实账本的推演，不是实测。
2. **接缝的 A/B 有一个混淆项。** 接缝开比接缝关便宜 37%、缓存读取少 59%、质量两边都全过，但**两边的请求数不一样**（10.7 vs 14.7）——模型随机，走的路不同。要说死这件事，需要固定 transcript 的对照实验（同段上下文跑两次），本轮没做。n=3 也只够说"指向明确"。
3. **真实费用仍大量未知。** 19,608 次请求里 16,481 次没有冻结价格；整树花费是情景。严格每完成任务费用仍是 null。
4. **来源 × 计费类型的精确归因仍不可得。** 供应商只回整请求的缓存/输入用量；`provider.request_profile` 只有 12 份样本（生产路径 2026-10-20 之后没有 PiG 流量），且只到 section 字节，不按计费类型拆分。本轮 CLI 补的是"前缀大小"和"用途"两个可测维度。
5. **节点泳道的压缩阈值没有同样的杠杆。** 节点泳道走内核的 `CompactionPolicy`（daemon 侧被显式关闭），本轮只覆盖 daemon 驱动的压缩。节点泳道占缓存读取 6.2%，优先级低，但结论不能直接套用。
6. **压缩调用未命中缓存的原因没有查到底。** 摘要请求的系统提示与工具集与会话不同，前缀对不上——这在 PiG 内部，需要上游支持才能改。
7. ~~压缩摘要的 9 次失败未修。~~ **已修**（§4.5）：根因是请求自己的输出预算被桥丢掉，摘要被按模型的整个上限要。已提交 `129da7e`，E2E 覆盖。
8. **reasoning 回放会增加输入 token。** 回放的 reasoning 是会话前缀的一部分，按缓存价计（比未缓存输入便宜 50 倍），但仍是净增。本轮没有测它对总花费的影响——它换来的是模型能读回自己的计划。
9. **模型、路由、effort、分工未动**，按目标书要求只提案。
10. **主会话与开发 CLI 路径各有一份实现。** 本轮 Go 与 TS 两边都改了压缩阈值，其余只改了 Go 路径。两条路径的行为差异（提示词拼装、请求装配）没有统一审计。
11. **首次全量门禁那一轮不可用。** 那一轮我在门禁运行期间改了被测源码（门禁会重建后端二进制），另一个会话同时在共享检出里跑测试。结果 23 个文件 / 58 项失败、含 EPIPE 与启动超时——**这是被测对象中途变化和资源竞争，不是回归**。最终以无并发改动的重跑为准。
12. **任务说明包复用的质量影响没有实测。** 它默认关闭，机制与红线（延续会话、本轮未压缩、说明未变）都有 E2E 覆盖，但"模型是否还记得自己绑定了哪些能力"只能靠真实模型的对照回答。
13. **大输出落盘已经做了（接缝）**，但固定评测任务集不产生大输出，所以端到端的钱只有自造的 big-output 任务量到了。 实测本机的 bash 输出中位数只有 247 字符，这条杠杆最多省约 8% 的上下文，却要改工具结果的形状——在压缩上限和说明包复用都落地之前，它的性价比排第四。
