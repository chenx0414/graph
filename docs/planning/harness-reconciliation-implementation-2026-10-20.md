本轮修复本地关联信息及错误用量假设；**未完成供应商侧权威恢复，历史未知仍未知，成本 A/B 仍停止**。供应商契约研究见[权威对账入口核验](harness-authoritative-reconciliation-2026-10-20.md)。没有新增真实模型调用、修改用户账号设置或联系供应商。

## 实际改动

每次受控发送继续使用正式调用 UUID；OpenCode Go 将该 UUID 放入官方代理支持转发的 `x-opencode-request-id`，不是幂等键。正文和 SDK 可见的供应商地址不重写。main、graph 节点、建议及沉淀候选调用都向正式 TaskStore 追加 `provider.transport` 事件，包含调用身份、时间、已序列化正文摘要、响应状态、允许列表内的响应请求 ID，以及有界嵌套错误名称/错误码。没有保存 auth、Cookie、完整错误对象或请求正文。

`fetch_started` 只证明进入本机 fetch，不能证明供应商收到请求，也不能当作额外费用。事件为尽力记录；丢失关联证据不能被推定为零用量。发生响应头前错误时只能保留待对账，客户端 ID 是否可从供应商日志检索仍待实际核验。没有给旧请求补造从未发出的 ID。

此前 429/503 的前两次容量重试被直接记成 authoritative 零用量。真实 HTTP 负例分别收到12次请求，CLI却只报告4次未知，其余8次被推定为零；官方兼容代理还会将下游网络失败转换为503，说明状态码不能证明零消耗。现503不再走容量重试，交给原始响应证据结算；429保留最多三次受控容量恢复，每次重试前将缺失用量记为未知，再经过准入。有限预算可以阻止后续发送，不限预算保持原有暂时限流恢复能力。不会把错误状态本身当作四类token证据。

保留429恢复是经行为验证的选择：首次移除所有HTTP容量重试后，原有真实文件任务在暂时429后未继续完成；恢复有界429重试但保留未知后，文件写入、读取、最终回复和成本CLI全部通过。缺失用量那次依然计入整树请求和unknownCost，不能声称完整成本已知。
