## Standards

**1 项 P2，PA05：新增凭据合并约束没有在配置保存前校验。**

位置：`src/server/start.ts:115–116`；对应保存路径 `src/server/config-service.ts:68–74`。

启动阶段新增“同一实际 key 的别名必须属于同一共享组”的规则，但配置保存只做原解析校验，不执行这项约束。正式 daemon 的 `/api/config` 可以保存冲突配置，返回 **200、revision:1、restartRequired:true**，并覆盖原有效配置。关闭后重启，连 view 模式也返回 **invalid_config**；用户不能再通过页面修复配置。

这与 `docs/architecture.md:89` 的非法配置同步返回可处理错误，以及待办 T02/T05 的“失败不覆盖有效配置”要求不符。不是风格意见。

主审独立复跑证据：`product-config-alias-conflict.mts` 和同名 `.output.txt`。初始配置有效，两凭据通过不同环境变量引用同一个合成 key；保存时为它们分配两个均已定义、上限有效的共享组。环境值在保存与重启间保持不变。

**实现建议**：保存与启动共用凭据身份/共享组校验；保存时使用宿主可解析的凭据身份，在原子替换前拒绝冲突并给出字段错误。校验不调用供应商、不泄露 key。

**关闭标准**：同 secretRef 和不同 secretRef 同值两种冲突均在保存时明确拒绝，原文件内容及 revision 不变；原有效配置随后仍可启动。修正为共同共享组后保存、重启和实际限流均通过。

其他：底层 scheduler 在调用者传入冲突 limit/group 时的合并策略可后续统一；本轮不把绕过 daemon 配置归一化的人造调用当作 PA01 未修复。无另立的风格阻断项。

### PA02-R1 · 等待恢复时没有重新获取全局 Agent 名额

位置：`src/runtime/pi-adapter.ts:84–95`；运行名额计数在 `src/core/execution.ts` 的 `occupiedSlots()`。

本轮把 waiting_slot=1 的操作排除出 Agent 名额计数，确实让 B 能启动。然而获得凭据名额后，适配器仅把 waiting_slot 直接清零，并未重新申请全局执行名额，也未检查当前名额是否已满。多个等待者恢复时因此能越过全局 10 的限制。

**独立证据**：`product-resume-execution-cap.mts` 使用真实 TaskRuntime、Pi 适配器和本地延迟 provider，沿用上一轮 PA02 的合成 scheduler 占位方式，把场景扩大到 20 个等待节点：

1. 先占用 key 的 20 个 API 名额，启动同 key 的 20 个节点，确认 queued=20、providerRequests=0。
2. 释放这 20 个合成占位；provider 对每次响应延迟一秒，并统计真实同时在途请求。
3. 观测 **providerInFlight=20、maxProviderInFlight=20、activeWorkers=20**，超过全局 Agent 上限 10。
4. 暂停任务并等待已有调用与 runtime 清理，正常退出。

这里 key 自身配置上限为 20，测试的是独立的全局 Agent 上限，不是在要求降低 key 上限。探针中的外部占位只控制“等待→恢复”的时机，未改写操作状态或执行名额数据库。

该反例直接违反 CONTEXT.md 的“运行名额：等待时释放，恢复执行前重新获取”，以及 PA02 关闭标准中的“同时保持 Agent 上限，释放、重试和恢复后不超发”。现有十个 A 加一个 B 回归在 B 完成后先暂停 A，再释放占位，因此没有执行恢复后实际发送的路径。

**实现建议**：用程序所有的状态转换协调凭据名额与 Agent 名额。等待结束后重新取得执行容量，取得两种必要名额后再重过发送门；取消、失败和暂停应归还各自拥有的名额，避免顺序反转导致死锁。`waiting_slot` 已影响正式调度，不能仅视为可吞掉写入错误的遥测标志。

**关闭标准**：

- 本探针恢复后，同时在途的 Agent 模型调用及实际执行 Agent 数始终 ≤10，其余保持等待；最终可完成，不死锁。
- 原十个 A 等待、独立 B 实际发送仍通过。
- 增加混合凭据、主管/工人、已有慢工具执行、恢复时暂停/取消、合法重试的组合；既不超 Agent 上限，也不超凭据/共享组上限。
- 不通过增加全局上限、提前释放仍在执行的 Agent、或吞掉状态写入失败来规避断言。
