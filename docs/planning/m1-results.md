## 入口及责任

- `openTaskRuntime({ stateDir, projects, actions })`：取得状态目录的单一所有权，升级 SQLite schema，恢复未终结操作。
- `runtime.user.begin/task/list`：用户任务入口。任务句柄提供 `say/accept/pause/resume/answer/view/watch`。
- `runtime.supervisor(taskId).propose`：仅有该任务的提案能力；没有确认、扩大权限、追加额度或用户答复能力。
- `runtime.host.runReady/report/reconcile`：可信宿主派发当前就绪节点、接收带代次结果、查询外部事实。`runReady` 推进一次当前就绪批次；每个调用仍有单独记录。
- `runtime.close()`：关闭新派发入口，等待宿主已启动的准备/执行/核对工作收尾后关闭数据库、释放所有权。外部 worker 是否停止必须由执行/核对 adapter 证明。

用户命令和主管提案使用独立能力对象，身份不由请求中的 `actor` 字段决定。这是进程内接口边界；HTTP 会话认证和 Origin 校验属于 G14。第三方代码不得获得用户或 host 对象，也不能直接成为宿主 adapter。

## 持久状态及恢复规则

正式记录包含项目、任务、不可覆盖的提案、节点与实例、幂等命令回执、全局递增事件游标、操作、验收证据、问题与答复、任务授权。SQLite 使用 WAL、FULL 和短事务，状态与对应事件一起提交。当前 schema 为版本 4，包含顺序事务迁移；更新版本的数据库会被拒绝打开。

确认前不能派发实现。需求追加会递增版本，旧版本提案无法确认；M1 确认后的范围固定，新增功能另建任务，确认后的范围调整协议属于后续版本化图和主管工作。当前活动任务完成验收后推进队列。

`view()` 返回需求消息、当前提案、节点、用量、问题、操作、证据和游标。所有读取在同一个无异步间隙的 JS 调用内完成，目录所有权阻止第二后台写入。`watch(after)` 只返回该任务在指定游标之后的更新；调用者按游标去重，关闭订阅不会关闭任务。它是 SSE 的数据基础，尚未提供 HTTP/SSE 服务。

| 已知事实 | 正式处理 |
| --- | --- |
| 只记录 intent，准备中暂停或重启 | 记为 not_sent，释放预留与名额；可重新领取，使用新 operation ID |
| 已记录 dispatched，进程消失或结果丢失 | 记为 unknown；保留预留，阻塞原节点，等待外部核对 |
| 外部核对证明完成且 worker 停稳 | 补记结果与用量，按原 operation 结算一次 |
| 外部核对证明没有发生且 worker 停稳 | 释放预留，新调用仍归属原实例及累计额度 |
| 外部仍不明或 worker 可能活跃 | 保持阻塞；worker 可能活跃时继续占名额，暂停状态为 pausing |
| 输出明确但 usage 缺失 | 保存输出，保留预留并建立 unknown_usage 问题；禁止直接重试 |
| 重复或冲突的结果 | 相同结果不重复结算；冲突结果不能覆盖已知结果或改变已结算状态 |
| 旧后台代次的 worker 结果 | 拒绝；新后台只能通过可信核对入口补记旧调用 |

所有权使用独立 rollback-journal SQLite 文件上的 `BEGIN EXCLUSIVE`，在后台生命周期内持续持有。操作系统在进程退出或 SIGKILL 后释放锁；没有通过 PID 超时推断“旧后台已死”的夺锁路径。操作状态、额度与单调递增代次在正式数据库中，不依赖锁文件内容。

## 调用、名额、额度和人工问题

每个 Agent 节点只创建一个实例，重试、等待和重启均保留该实例。默认累计额度 20,000,000 tokens。usage 使用互不重叠的 input、output、cacheRead、cacheWrite 分项；已包含在 output 中的推理量不再另加。预留不足时建立预算问题，不创建新调用。已知实际用量超过预留时仍如实记账，后续工作等待用户确认异常；追加额度仅能通过对应问题的用户答复完成。

Agent 的准备/实际执行以及可能仍存活的 worker 共用 10 个名额，主管计入。等待人工答复释放名额，答复后重新竞争名额。程序节点单独限制为同时最多 4 个准备/执行操作。手动暂停在实际 dispatch callback 前重新检查；检查、持久 dispatched 和调用 callback 之间没有 await 间隙。已发送操作可以结束，未停稳前不报告 paused。

问题包括额度不足、用量未知、预留超额、权限不足、等待答复、adapter 不可用/准备失败和恢复核对。答复限定在原任务和问题类型；答复一个问题不会解除其他问题或手动暂停。授权只能匹配可信 adapter 请求的 capability 字符串，并作为该任务的授权持久保存。外部副作用仍不明时必须由可信宿主核对，不提供任意重做的用户答复；输出已经明确而仅缺用量时，用户可提交 usage 和证据说明。任务配置恢复失败整体回滚并释放所有权。

## Adapter 合约与本轮边界

`ActionAdapter.prepare(operation)` 只能做无外部副作用的准备，返回的 callback 才实际发送一个操作。callback 成功返回表示该操作的 worker 已停稳；失败不能据此证明外部动作未发生。`reconcile` 只查询事实，必须给出证据说明及 worker 是否停稳。一个 callback 不能包住包含多次模型/工具请求的完整 Pi prompt。生产下层调用仍需逐一进入本内核。

M0 的 `CallBroker` 保留为独立可行性验证。M1 的正式操作、预留与结算都在同一 TaskStore 中，没有双写 M0 的单实例数据库。G09 将生产 Pi 下层调用接到此处，并继续运行 M0 的实际请求契约测试。

M1 支持固定 DAG、顺序和独立就绪节点，检查节点必须是程序节点；验收证据必须来自指定检查节点，包含绝对产物路径、SHA-256、operation、需求版本及提案版本。程序检查必须提交对应验收项的证据，Agent 的自报通过不能代替检查。这里依赖可信程序 adapter 实际验证产物；跨代码变更/提交的证据失效、动态图、路由、回环、容器、三种完整验证器、自动集成与合并仍是 G06–G13 的工作。

尚无常驻 HTTP/Web 宿主或实际供应商集成。示例和测试中的 adapter 是可信脚本；第三方 Pi、MCP、安装器的 OS 约束继续沿用 M0 路线，在 G09/G10 接入生产宿主。

## Standards

首次独立审查发现 1 项 P2：用户解除最终阻塞时只更新节点，未完成任务和推进队列，违反 ADR 0003 的正式状态一致性要求；分散的收尾逻辑也是可能的 Shotgun Surgery。已提取同事务内的 `advance(taskId)`，由结果结算和用户答复共用。最终独立复核确认该问题已解决，无剩余规范问题。

## Spec

首次独立审查发现 2 项实现错误，无 M1 独立缺项或范围扩张：

- P1：达到额度上限后仍允许预留为 0 的调用。已独立检查 `used >= budget`，跨重启回归证明没有发送新调用。
- P2：最终人工答复没有完成任务和推进队列。已统一完成判断，回归检查任务完成、后继激活事件及后继执行。

另由本地复查补齐 3 条回归：迟到的冲突回调不能覆盖已结算状态；恢复后输出明确但 usage 未知时转入对应人工问题；项目注册失败不能留下部分配置。各项均先复现失败，再验证修复。

Spec 最终独立复核确认两项问题均已修复，无剩余发现；同时复核了迟到回调、未知用量转换和项目注册回滚。两位复核者检查了实现与回归测试，完整测试运行由本轮主执行者完成。
