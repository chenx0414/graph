## 返工项

### PA01 · P1 · 同一实际 key 的凭据别名绕过并发上限（T02/T04）

**位置**：`src/server/start.ts:99–111`、`src/runtime/model-scheduler.ts:44–50`。

宿主直接用配置的 `credentialId` 作为限流身份；解析器允许多个凭据引用同一 secretRef，也未强制这些别名归入同一共享组。调度器因此把同一实际密钥视为不同配额池。

**独立证据**：`product-key-alias.mts` 调用实际受控 OpenAI 发送路径、本地延迟流式 provider；两个不同 credentialId 使用同一个合成 key，每项 limit=1，真实 Authorization 对应的最大在途数为 **2**，两次请求均成功。本探针验证发送层；宿主将配置别名原样传入该层由上述源码确认。现有 aliases 测试固定同一个 credentialId、使用不同 key 字符串，不能证明此要求。

**实现建议**：宿主按供应商实际凭据建立内部规范化身份，或在配置阶段强制同一实际凭据共享受限组。相同 secretRef 和不同 secretRef 解析为同一值都要处理；明确别名上限冲突策略，不能把明文 key 暴露给 UI。

**验收标准**：真实 daemon 配置两个模型、两个凭据别名、相同合成 key；limit=1 时实际 key 在途数始终 ≤1。再验证不同 secretRef 同值、共享组、独立 key 并行与脱敏。

### PA02 · P1 · 等待 key A 会阻塞独立 key B（T04）

**位置**：`src/core/execution.ts:214–217` 与 `src/runtime/pi-adapter.ts` 的 scheduler 等待衔接。

等待 provider 名额的操作仍是 worker_active，继续占用全局十个 Agent 执行名额。即使凭据调度器本身跳过阻塞队列，执行层也不会启动后面的独立凭据节点。

**独立证据**：`product-independent-key.mts` 使用真实 TaskRuntime 与受控 provider，先占用 A 的唯一名额，再放入十个 A 节点和一个独立 B 节点。结果：**queuedA=10、activeWorkers=10、providerRequests=0，B=pending**。最后暂停任务、释放合成占位并等待清理，命令正常退出。

**实现建议**：把等待 API 名额与占用 Agent 执行名额协调起来；等待可释放执行容量，恢复时必须重新取得容量并重过发送门。不要仅通过增加全局上限掩盖问题。

**验收标准**：A 持续排队时 B 可实际发送；同时保持 Agent 上限、暂停/取消、用量与代次语义。至少覆盖十个 A 等待者加一个 B，释放、重试和恢复后不超发。

### PA03 · P2 · 新任务记录尚未生效的配置版本（T02/T05）

**位置**：`src/server/start.ts:172`、`src/core/task-runtime.ts:121`。

运行时项目、模型和凭据绑定取启动时配置，但 task.created 的版本读取配置存储的最新 revision。保存返回 restartRequired 后，两者立即脱节。

**独立证据**：`product-config-revision.mts` 通过正式 daemon 和配置 HTTP API，从 revision 0 保存 revision 1，返回 `200 / restartRequired:true`。未重启时仍只能使用旧项目配置，新建任务却记录 **configRevision:1**。

**实现建议**：区分持久化版本与当前运行版本；任务绑定当前实际运行的不可变配置版本。页面明确展示待重启版本，连接测试也应说明测试哪个版本。

**验收标准**：保存前后及重启后分别创建任务，记录版本与实际项目/端点/key/limit 一致。保存后未重启的任务不能冒用新版本。

该探针还观察到配置移除的旧项目在重启后仍出现在项目列表；请检查持久化项目目录与可新建任务项目列表的边界，保留历史记录不应自动等于仍允许创建新任务。本项作为同一配置生效复验的附加检查，不另立已完成闭环的发现。

### PA04 · P2 · 图节点已完成，记录和证据仍停留在旧状态（T03/T06）

**位置**：`src/web/App.tsx:421–429`。

GraphPanel 的 SSE 只触发 graph reload；task view 和 operations 仅在首次进入或依赖参数改变时加载，完成事件不会刷新它们。

**独立证据**：`product-live-records.mts` 使用真实 GraphServer、TaskRuntime、构建产物与无头 Chromium。页面打开待执行节点后驱动完成：graph 请求从 4 增为 8，view 和 operations 请求始终各 1。页面显示 **“已完成 / 输出版本 1 / 验收证据 无 / 操作记录（0）”**，后端已有 succeeded 操作与有效证据。

**实现建议**：同一任务事件驱动图、节点记录与证据一致刷新；合并重复请求，并给异步请求加任务身份/请求代次校验。当前 useAsync 也缺少防止旧任务慢响应覆盖新任务的保护，需要一并加乱序响应回归；后者本轮仅做源码检查，未计为独立复现项。

**验收标准**：不离开图页、不点击“加载更多”，运行中→完成/失败/等待后的记录与证据自动更新；快速 A→B 切换并使 A 响应迟到，B 页面始终只展示 B 的数据。
