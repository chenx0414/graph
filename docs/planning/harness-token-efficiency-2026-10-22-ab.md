## 5. 真实模型 A/B（command-goat 订阅内、边际费用 0 的模型）

模型：`command-goat:deepseek/deepseek-v4.1-flash`（`https://api.commandcode.ai/provider/v1`，凭据只经环境变量 `GRAPH_SUBSCRIPTION_COMMAND_GOAT_API_KEY` 传入，仓库与报告里都没有密钥）。**跑的是 Go 后端**（桌面应用真正跑的那个），不是开发路径的 TS 服务。

**关于"免费"这个词的口径**：这个模型走的是**订阅覆盖**，**边际费用是 0**——同一轮里多跑一次不额外花钱。供应商另外还有一批带 `:free` 后缀的模型，**本轮没有用**它们：两个模型的行为不同，换模型会把"harness 的差别"和"模型的差别"混在一起。**A/B 要比的是 harness，所以模型必须固定。**

**如果按字面取义（用 `:free` 后缀的模型），这条路通不通？** 通，但得换模型重跑。2026-10-23 用 harness 真正会发的请求形状（流式 + 工具声明）探了供应商当前的模型清单（92 个，其中三个带 `:free`）：

| 模型 | HTTP | 发不 发工具调用 | 说明 |
| --- | --- | --- | --- |
| `deepseek/deepseek-v4.1-flash`（本轮用的） | 200 | 发 | |
| `stealth/glyph-cluster:free` | 200 | **发**（`finish_reason: tool_calls`） | 输出预算给到 512 才发得出来；给 64 时它先说了一堆话，没落到工具上 |
| `reflection/beam:free` | 200 | **发**（`finish_reason: tool_calls`） | |
| `poolside/laguna-s-2.1-free` | **429** | — | 上游暂时不可用（两次都 429） |

**所以三个 `:free` 模型里有两个能驱动工具循环**，字面取义是可做的，只是要用 `stealth/glyph-cluster:free` 或 `reflection/beam:free` 重跑整组 A/B，而且 `stealth` 每一轮要的输出预算更大——**那会让它成为另一种负载形状**，和本轮的数字不能直接比。换句话说：**本轮报告里的所有数都建立在 `deepseek/deepseek-v4.1-flash` 上；换成 `:free` 就是另一份实验，结论要重新量。**

计价用的是模型目录里的同一套权重（见下），比的是工作量，不是账户档位。

计价说明：订阅内实际花费是 0，所以 A/B 用**同一套权重**折算钱——`input 0.15 / output 0.6 / cacheRead 0.003` USD 每百万 token（DeepSeek V4 Flash 的 off-peak 价，见模型目录）。比较的是**工作量**，不是账户档位。

驱动脚本：`scripts/harness-ab-eval.mjs`。每个变体在**每一轮内部交替**执行（暖缓存或慢的一分钟不会只落在一边），每个变体跑完后读这次运行自己的账本（`scripts/harness-cost.mjs`），行为检查由 case 自带的独立校验程序在 Agent 之外运行。

### 5.1 parser 任务（修 config.js），每组 3 轮 + 2 轮补跑

| 变体 | 轮次 | 行为检查 | 请求 | 输入 | 输出 | 缓存读取 | 花费 | 平均前缀 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default | #0 | ✓ | 19 | 24,800 | 5,898 | 176,256 | $0.007788 | 9,277 |
| default | #1 | ✓ | 14 | 15,456 | 6,571 | 129,792 | $0.006650 | 9,271 |
| reuse | #0 | ✓ | 24 | 29,077 | 6,435 | 237,312 | $0.008934 | 10,318 |
| reuse | #1 | ✓ | 13 | 13,934 | 5,177 | 111,616 | $0.005531 | 8,586 |
| ceiling-low（8,192） | #0 | ✓ | 33 | 43,699 | 22,486 | 428,032 | $0.021331 | 13,376 |
| ceiling-low（8,192） | #1 | ✓ | 20 | 25,319 | 10,727 | 168,448 | $0.010739 | 8,422 |

均：default $0.007219、reuse $0.007233、ceiling-low $0.016035。

**读出来的三件事**：

1. **质量没有下降**：8 次运行（含补跑）全部通过独立行为检查。
2. **同一个变体在同一个任务上的波动是 2.2 倍**（default 的 $0.0067–$0.0149）：模型每次走的路不一样（工具调用次数 14 vs 19 vs 24），请求数一变，token 就变。**在这个样本量下，2 倍以内的差异都读不出来。**
3. **8,192 的压缩上限明显更贵（2.2 倍）**，而且机制说得通：这个任务的自然上下文约 9,300 token，本来就在上限之下，所以它是被**反复**压缩的；每次压缩是一次独立的计费调用，读的是整段（被截断过的）历史。**上限必须远高于任务的自然上下文大小**——生产负载的自然上下文是 496K，128K 的上限对它有意义；这个短任务上没有。

**结论（负结果也要记）**：短任务上，任务说明包复用（每次 operation 省约 875 token，占 9,300 前缀的不到 1%）**测不出来**；压缩上限在 131,072 对短任务**完全没有触发**（null 结果）；8,192 的激进上限**是负收益**。这三个都不是"改动没用"的证据，而是**这个任务集的规模测不出这两个杠杆**——它们的收益在生产负载的长会话里（上下文 496K、62 次 operation、每次请求重读整段）。

### 5.2 command 任务（跑 check.mjs，输出 5,000 行）：任务集本身不产生大输出

这个任务会打印 5,000 行诊断输出（约 70KB），正是工具结果接缝要处理的东西。对照：`default` = 接缝开，`no-seam` = 接缝关（`GRAPH_TOOL_RESULT_SEAM=0`），各 4 轮。

| 变体 | 行为检查 | 均花费 | 均请求 | 均输入 | 均输出 | 均缓存读取 | 均前缀 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default（接缝开） | 4/4 ✓ | $0.003702 | 10.8 | 13,956 | 2,284 | 79,584 | 7,430 |
| no-seam（接缝关） | 4/4 ✓ | $0.003483 | 10.0 | 14,730 | 1,772 | 69,920 | 6,915 |

**差 6%，而同一变体内部的波动是 40%**（default $0.002966–$0.005013，no-seam $0.002901–$0.004069）。读不出差异。

**为什么读不出——去看了一次留档的运行**：12 条工具结果，最大的 819 字符，**没有一条超过 4,000 字符**。**Agent 根本没有运行 check.mjs**：它读了 settings.json，把 mode 改成 fast，结束。（验证程序自己跑 check.mjs，所以验收照样通过。）**这个任务压根没有产生大输出**，接缝无事可做。

这是本轮 A/B 最有价值的一条方法论：**固定评测任务集不产生大工具输出，也就不可能量到工具结果接缝。** 接缝本身由 E2E 直接证明（模型拿到句柄、句柄里每一行都在），但端到端的钱要另配一个真的跑命令的任务。

### 5.3 big-output 任务（强制跑出 5,000 行输出）：接缝的机制与它的真实幅度

同一个 check.mjs，但提示词要求"运行 node check.mjs 并读完它的完整输出"。**接缝确实被触发了**——留档的一次运行：

| | 大小 |
| --- | ---: |
| 命令的真实输出 | 78,934 字符 / 5,006 行 |
| 模型读到的 | 19,959 字符，形如 `[large tool result: 78934 chars, 5006 lines]` + 句柄 |
| 句柄文件里的 | 78,934 字符（逐字节齐全） |
| 这次运行的工具结果总量 | 22,617 字符（原始输出的话是 78,934+） |

**端到端的钱（n=11/组，共 22 次通过行为检查的运行）**：

| 变体 | 均花费 | 中位花费 | 均缓存读取 | 中位缓存读取 | 均请求 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 接缝开 | $0.005291 | $0.005261 | 128,582 | 121,984 | 12.2 |
| 接缝关 | $0.005381 | $0.004633 | 149,108 | 105,472 | 12.4 |

**花费差 −1.7%（标准误 $0.00086，t = −0.10）；中位数上接缝开还贵 13.5%。这个差距测不出来。**

前面报过的 −37%（n=3）、−15.6%（n=7）都是抽样运气——加到 n=11，均值差缩到 −1.7%，中位数甚至反向了。**本报告一度把接缝排到第 0 位，那是基于一个不成立的统计结论；现在按证据重排。**

**而"测不出来"本身是这轮最有价值的发现——它说明了杠杆的兑现条件：**

一个前缀的节省值多少钱，取决于**缓存读取占这次任务花费的比例**：

| 负载 | 平均前缀 | 缓存读取占花费 | 同样省 17.8% 的前缀值多少 |
| --- | ---: | ---: | ---: |
| 这个短任务（上下文 ~12K token） | 12K | **8%** | 1.4% |
| 生产会话（上下文 246K token） | 246K | **42.7%** | 7.6% |

**短任务上省前缀几乎不值钱**（缓存读取只占 8%），所以接缝、说明包复用、压缩上限在这个任务集上全都不显形——不是改动没用，是**这个任务集的花费形状不奖励省前缀**。生产会话的形状正相反。

于是把生产负载的账本代进去，三个杠杆的**生产规模价值**（前缀缩减 × 缓存读取占花费的份额）：

| 杠杆 | 实测前缀缩减 | 生产规模花费影响 | 证据等级 |
| --- | ---: | ---: | --- |
| 压缩上限（128K） | −69%（推演） | **−29%** | 推演；接缝开着时它不触发 |
| 任务说明包复用 | **−17.6%**（21 轮长会话实测） | **−7.6%** | 前缀缩减实测；花费影响代进去 |
| 工具结果接缝 | −5.2%（生产历史，工具结果字节 −10.5%） | **−2.2%** | 字节实测；端到端花费在短任务上测不出 |

**排序回到"先压缩上限，再说明包复用，接缝是兜底"**——但这次每一条的证据等级都标清楚了。

**还有一条值得记的**：接缝开的运行平均请求数与接缝关基本相同（12.2 vs 12.4）——**在这个任务上接缝没有改变模型走的路**，省下的只是它读到的那段文本。这比早先 n=3 时"少 1.8 次请求"的解释更朴素，也更可信。

**为什么前两次跑没成**：第一次 daemon 进程死了（stderr 为空 = 被 SIGKILL）；查了机器状态——可用内存 384MB、swap 已用 3.9GB、另一个会话同时有 18 个 vitest/graphd 进程。第二次（接缝关）没有死，但那一轮 turn 停在 pending：Agent 读了两个文件就卡住。**同一份代码第三次跑就正常完成并通过验收**。所以这两次是环境与免费档的不稳定，不是改动的回归——但我也没有把它们从记录里抹掉。

### 5.4 长会话（21 轮同一会话）——两个 flag 在真实长度上是什么表现

短任务量不到东西，所以把同一个会话拉长到 21 轮（首轮 + 20 轮追问），三个变体各 1 轮：

| 变体 | 行为检查 | 请求 | 花费 | 未缓存输入 | 缓存读取 | 平均前缀 | 压缩次数 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default | 1/1 ✓ | 49 | $0.012068 | 29,327 | 775,168 | 15,820 | 0 |
| setup-only（复用任务说明包） | 1/1 ✓ | 46 | $0.012162 | 35,380 | **638,592（−17.6%）** | 13,882 | 0 |
| ceiling-32k（复用 + 32K 上限） | 1/1 ✓ | 48 | $0.012119 | 40,857 | **622,464（−19.7%）** | 12,968 | **0** |

**三件事**：

1. **质量**：21 轮里每一轮都只发一次任务说明包，行为检查依然全过——模型没有因为说明不再重复而忘记自己绑定了什么。
2. **任务说明包复用确实在起作用**：缓存读取 −17.6%，和预测的"去掉 20 份重复说明"吻合。但**总花费是平的**（+0.8%）——省下的缓存读取被上升的未缓存输入抵掉了。n=1，这个幅度也在轮间波动范围内，所以只能说"机制看得见，钱没省下"。
3. **32K 的压缩上限一次都没触发**（压缩次数 0），尽管会话有 21 轮。**因为接缝已经把上下文压住了**：21 轮的平均前缀才 15,820 token。

**这是本轮最有价值的一条结论**：**接缝（直接改）和压缩上限（flag）是替代关系，不是叠加关系。** 接缝让大输出不再撑大上下文，上下文就不再逼近窗口，压缩阈值就基本不参与事了。压缩上限真正还有用的场景是：**接缝关掉的长会话**，或者**长到几十万 token 的会话**。上一轮我推演的"128K 上限省 29%"是建立在"上下文能长到 496K"这个前提上的——而那个前提正是接缝要消灭的东西。

**所以排序要改**：先修接缝（它是直接改，且有真实模型的数），再谈压缩上限；两个 flag 一起开着，只是在没被接缝压住的长会话里多一道保险。

### 5.5 往生产形状靠：15 轮长会话与 8 轮大输出

§5.2 说短任务量不到东西，于是把会话拉长。两组：

**A. 15 轮的 `command` 任务**（每轮追问"再跑一次检查"）——每组 2 轮：

| 变体 | 行为检查 | 均花费 | 均缓存读取 | 均前缀 | 压缩次数 |
| --- | --- | ---: | ---: | ---: | ---: |
| default | 2/2 ✓ | $0.012835 | 572,352 | 14,500 | 0 |
| ceiling-32k | 2/2 ✓ | $0.008654 | 505,856 | 13,120 | 0 |
| no-seam | 2/2 ✓ | $0.009387 | 580,416 | 14,882 | 0 |

**压缩一次都没触发**：15 轮之后上下文只到 ~14K token。原因是 **Agent 跑过一次 check.mjs 之后就不再跑了**——它记住了结果。于是这个"长会话"并不长，上限自然不触发。

**B. 8 轮的 `big-output` 任务**（提示词要求"读完它的完整输出"，每轮都逼出 5,000 行）：

| 变体 | 行为检查 | 均花费 | 均花费范围 | 均缓存读取 | 均前缀 |
| --- | --- | ---: | --- | ---: | ---: |
| default（接缝开） | 2/2 ✓ | **$0.012534** | $0.011862–$0.013206（**11%**） | 466,432 | 16,082 |
| no-seam（接缝关） | 2/2 ✓ | $0.013816 | $0.008955–$0.018677（**2 倍**） | 742,336 | 23,947 |
| no-seam + 32K 上限 | 2/2 ✓ | $0.013533 | $0.008959–$0.018107（2 倍） | 464,960 | 15,194 |

**两条读得出来的东西**：

1. **接缝开着的时候，上下文稳在 16K；关掉它，同一任务能长到 34K。** 这就是接缝的作用——它把"一次大输出"从"一段永久的前缀"变成"一句摘要 + 一个句柄"。
2. **接缝开着的那两次运行，花费几乎一样（11% 的带宽）；关掉它的两次，差了 2 倍。** 因为上下文不再能鼓起来，这次任务花多少取决于模型这一轮又跑了几次大命令。n=2，这只是提示，但方向和机制一致。

**仍然没测出来的**：32K 的压缩上限**一次都没触发**——上下文峰值 34K，而触发点是在每一轮开始时按上一轮记录的上下文判断的。这个任务还是够不到那个形状。

**于是"生产形状"这件事本身的结论是**：它不是把会话拉长就能得到的。生产的 496K 上下文是 62 轮**重**工作（工具输出大、每轮做的事多）攒出来的；脚本化的评测任务跑 8 轮、每一轮都问同一件事，上下文只到 16K。要复现那个形状，需要一个真的重、真的长的任务——那不是这种脚本化 A/B 能给的。

**所以这三个杠杆的端到端钱，仍然没有实测出来。** 这一轮把"怎么测"这件事推进了一步：知道要用长会话、要用真的每轮都产出大输出的任务、知道接缝真正的作用是**让上下文不再鼓**（以及让轮间花费不再散），也知道了压缩上限在什么样的上下文长度上才会真的参与。

### 5.6 换成真账本算：把每次请求的前缀逐条重建

脚本化的 A/B 量的是"这次任务花多少"，而真正决定花费的是**每一次请求带了多少前缀**。生产库里那条主会话的真实 transcript 还在：2,087 条 durable entry、1,043 个助手消息（= 1,043 次请求）、每条工具结果和每份说明包的字节数都在。

按这条**真实的请求序列**重建：第 k 次请求的前缀 = 静态前缀 + 它之前所有内容。然后把两个改动分别套上去，再看总账：

| 变体 | 该会话的缓存读取 | 省下的 | 换算到整个真实 task |
| --- | ---: | ---: | ---: |
| 照录 | 121,933,859 token | — | 3,263,080,429 token（$9.79） |
| + 工具结果接缝 | −13.7% | 16,686,328 token | **448,115,091 token = $1.34** |
| + 任务说明包复用 | −9.7% | 11,835,958 token | **317,857,319 token = $0.95** |
| 两个都上 | −23.4% | 28,522,286 token | **765,972,410 token = $2.30** |

**为什么百分比和"平均前缀"算出来的不一样**：一个工具结果省下的字节，会被**它之后的每一次请求**再读一遍。省下的是"每次请求的前缀"，不是"上下文里的一次"。

**对照整棵树的花费**（情景 $28.44，缓存读取占 42.7%）：接缝 −4.7%、说明包复用 −3.3%、两个一起 −8.1%。而压缩上限（如果它在生产负载上触发）仍是最大的那条（−29%）。

**这改变了两件事**：

1. **接缝不是"兜底"，它是第二条杠杆**（生产规模 −4.7%，可与说明包复用叠成 −8.1%）。上一版报告按"平均前缀"估成 −2.2%，**低估了一半**——因为省下的字节要乘以后每一次请求。
2. **"省前缀"在短任务上不值钱这条仍然成立**：上面的钱是按真实请求序列算的，脚本化 A/B 量的是同一个机制在短上下文上的表现，两者不矛盾。

**这是推演，不是实测**：它把真实请求序列和真实字节套上真实的费率，没有让模型重跑一次。要把它变成实测，缺的就是一个"真的重、真的长"的任务——§5.5 说清了那不是脚本化评测任务能给的。

### 5.7 与 §5.8 移到了[重跑一节](harness-token-efficiency-2026-10-22-ab-rerun.md)

这两节在当前分支的代码上把 A/B 又跑了一遍，**逐次原始账本进了仓库**：§5.7 一轮（n=6/组）、§5.8 八轮（n=2/组），18 次运行 18/18 通过独立行为检查。

**要点**：接缝**把前缀压小 18.2%（一轮，t=−2.13，显著）/ 25.2%（八轮）**；但一轮那组**把字节从"缓存读取"挪进"未缓存输入" 40.4%（t=+2.40，显著）**，所以花费测不出（+14%，t=+1.30）。**接缝是"省前缀的杠杆"，不是"省钱的杠杆"。**
