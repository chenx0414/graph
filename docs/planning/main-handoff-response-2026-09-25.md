# Main 回复被交接摘要打断

2026-09-25，conversation `193ce3e1-092d-460d-b2c1-c6a91434c7d2`。

## 证据与边界

- 北京时间 09:55、09:58、10:00 的 Pi assistant 记录分别为 `4aaf5560`、`1cf770c4`、`817e1778`。三条均从工作说明突然转入 `<analysis>` 和九节 `<summary>`，以普通 `stop` 结束，约两万字符；不是 reasoning content。
- 调用账本记录为 `completion`。最近一次正式压缩在 09:06，格式为 `## Goal`，并无上述回合的压缩事件。
- 用 SDK `buildSessionContext` 重建首次异常前的 520 条消息，没有发现这套标签、标题或要求总结会话的指令。异常前的工具结果是正常测试失败输出。
- Graph 将普通成功回复直接作为成功回合持久化。异常文本随后也会重新发送给模型；用户引用异常要求纠正后，仍出现相同模式。
- 定位到了模型回复通道中的行为异常及 Graph 缺少恢复处理。没有保存当时原始 HTTP 字节，不能进一步断言是 DeepSeek 自身还是 OpenCode Go 上游服务造成，也没有证据证明 300k 上下文是触发阈值。

## 修复

在主对话的受控模型流外包一层窄范围恢复，识别实际观察到的“工作说明 → 自我分析会话 → 编号交接摘要”格式。普通摘要、XML 和代码示例不依赖单个标签判定。正式压缩、建议生成和功能节点不启用此恢复。

疑似标签之后的流暂缓展示，直到能判断完整响应。识别为异常后不把摘要写进 session，也不把它作为下一次请求的输入；通过原有调用门纠正一次。此前工具结果继续保留，不重新运行工具。一个 operation 的所有请求共享这一次机会；再失败就明确报错，不误报成功或无限续跑。每次实际发送仍独立计量。

对历史中相同的坏 assistant 回复，只在发送模型时替换为“该回复没有完成任务”的说明，原始会话记录不改。用户消息不删除。恢复事件 `session.handoff_response` 仅保存 operation/node/status，不保存摘要或凭据。

这是对已观察模式的有界恢复，并非上游模型行为已被根治的证明。其他格式不应未经证据扩大匹配规则。

## 验证

- 真实 OpenAI SSE → controlled stream 的失败测试先复现：旧实现仅发送一次并接受异常回复。

- 覆盖连续失败、同 operation 的纠正次数、历史输入替换、不改原始历史、正式压缩旁路和正常摘要/代码示例。
