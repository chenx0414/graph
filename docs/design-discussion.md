# 设计讨论

原始构想见 [draft.md](draft.md)。本文记录访谈中已确认的范围与待解决问题；草稿中的其余设想仍待讨论。

## 已确认

- 第一位使用者是项目作者本人。
- 首版场景：向已有项目添加一个边界明确的功能。
- 当前痛点：大型任务难以在一次对话中完成；使用者需要手动拆解任务、交给不同 Agent，当前流程只能串行，还需要人工盯进度、转发上下文。
- Pi Agent 和 TypeScript 是硬约束。作者选择 Pi Agent 的理由是开源、简洁，以及可借用的文档和扩展；选择 TypeScript 的理由是认为它比 Python 更适合本项目的大型开发需求。
- LangGraph 和 Rust 是候选技术，尚未决定采用。
- 首个真实验收项目为 `/Users/macmini/workspace/12-MediaBookmarks`，已确定 B站本机 Web 应用闭环；具体交互在该功能任务的需求讨论中细化。
- 输入流程：先与使用者讨论需求，形成可验收的说明，再进入执行。
- 实现、审查和返工自动推进；遇到实质需求歧义或预算耗尽时请求使用者介入。
- 完成交付包括可检查的代码修改、测试结果、审查结论和合并；发布由使用者决定。
- 首版展示系统生成的任务图和运行状态，允许暂停、补充说明和继续；无需手工编辑图。
- 首版在本机运行；关闭界面后继续执行，程序重启后可从保存的进度恢复。
- 各 Agent 的修改先汇入任务集成分支；整体测试和独立审查通过后，自动合入启动任务时指定的目标分支。
- 允许并行写代码，各 Agent 使用独立工作副本；明确依赖的修改串行执行。共享空间存放任务说明、证据和产物，代码通过合并集成。
- 暂停时让正在执行的调用结束后停住；补充说明后重新评估受影响的任务，再继续。
- 同时运行最多 10 个 Agent，主管计入；每个 Agent 累计 token 上限 20,000,000，按输入与输出计量，缓存输入计一次。重试和恢复不重置额度，耗尽的工作需用户追加额度。运行时长不限。
- Graph 采用本机 Web 界面，后台执行独立运行。MediaBookmarks 首个验收版本也采用本机 Web 应用，复用已有 CLI 能力。
- MediaBookmarks 首版闭环：B站确认登录状态 → 发起采集 → 查看进度与失败原因 → 浏览收藏及已有笔记 → 导出 Markdown。其他平台保留现有 CLI 能力，后续再接入界面。
- 连续 3 轮没有实质进展时保存现场，向用户提供争议、尝试与证据并等待介入；有进展时继续，直到通过或额度耗尽。
- 主管可以在已确认需求与额度内自主调整任务图，每次保存原因和版本。新增需求、改变验收标准或突破额度时需用户确认。
- Agent 提交结果、证据和状态变更请求，由 Graph 执行程序统一校验并记录。主管负责规划与返工，程序负责执行规则、额度和状态一致性。
- 系统自动生成任务说明包，含目标、验收条件、相关决策、依赖产物和文件位置。子 Agent 保有独立会话，可读取共享资料或向主管提问；完成后提交结论与证据，主管按需查看完整记录。
- 恢复时复用有证据的已完成步骤；中断模型调用重新发起并计入额度；Git、文件写入等先核查实际结果再补做。无法确定且重复执行可能改变外部结果时找用户。
- 自动允许任务工作副本内代码修改、构建测试、依赖安装和资料检索；主管可在用户预先授予范围内批准额外目录写入和外部服务操作。新增 Agent 继承任务权限上限，由程序落实；扩大任务权限、追加额度与发布仍由用户决定。
- 实现与审查要求不同模型、独立上下文，不强制不同厂商。执行中可从预配置候选切换模型，对应审查需避开参与该轮实现的模型。
- main agent、Master Agent 与主管指同一个角色，即直接与用户对话的 Agent。
- 允许执行中自主搜索和安装新的 Skills、MCP 与扩展；不要求逐次人工确认安装。安装至 Graph 管理的能力库，记录来源与版本，能力安装不自动扩大任务权限。
- 缓存输入按每次请求计入累计用量；“计一次”指同一次请求不重复相加。
- 额度作为新调用准入门槛，尽量预留本次输入与最大输出；达到上限后禁止新调用，实际超出仍完整记账。用量缺失标记为待核对，并暂停该 Agent。
- 暂停后所有已发出的调用可以结束，但不再发起下一个模型或工具调用；全部停稳后显示已暂停。
- Agent 实例与其 Agent 节点一一对应，同一实例不能承担多个节点。同一种 Agent 可以派出多个实例，分别对应不同节点。审查不通过沿回边返回原实现节点，由同一实例返工，保留会话与累计额度。
- 新能力安装到 Graph 管理的能力库，记录来源和版本，后续任务可复用；运行中实例沿用原定义版本，后续实例可使用新版。
- 首版主管通过程序创建接口创建 Agent；程序校验模型、能力、权限和并发限制。独立的 Agent 创建者角色留待后续。
- 一轮指实现或修复 → 检查与审查。有证据关闭阻塞问题或通过此前失败的验收项才算实质进展；改写说明、重复修改、跳过失败测试不算，检查标准变化必须可追踪。
- 首版一次执行一个功能任务，其余排队；该任务内部最多 10 个 Agent 同时运行，主管计入。
- 保留 Agent 节点和程序节点。测试、合并、条件判断可由程序节点执行，不占 Agent 名额；普通工具调用不必展开为独立节点。
- Agent 库相当于人才库，库定义预先配置 Skills、MCP 等并可复用，具有推荐模型等级。Q38 明确修正此前模型身份的歧义：模型不属于 Agent 身份定义，同一个库定义可以使用不同 LLM；每次派出的是独立实例，完整运行配置包含库定义版本和实际模型。
- 10 个名额限制正在执行的 Agent；等待依赖或结果时释放名额，恢复前重新获取，会话、节点身份及额度保持。主管执行时同样占一个名额。
- 需要人工介入时，仅暂停受影响节点和依赖它的后续节点，独立分支继续；涉及整项需求或任务权限时暂停全任务。界面集中展示待处理问题并保存现场等待回复。
- 主管可自主创建并保存 Agent 库条目；更新产生新版本，正在运行的实例继续使用原版本，后续实例可采用新版。
- 首版由用户配置可用模型、等级与使用偏好，主管据此选择。切换模型保持原节点、实例、工作副本和累计额度，记录切换并交接已有上下文；无满足条件的候选时暂停该节点等待处理。
- 目标分支有新变化时，先纳入任务集成分支，重新运行受影响的测试和审查，再合并；冲突需要改变已确认需求时找用户。
- 首版支持原始草稿的全部图模式：扇出扇入、主管-工人、流水线、路由、评估-优化循环，以及对抗式、多视角、评委式验证器，允许组合与嵌套。
- 需求讨论结束时固定验收项，由程序记录每项检查方式和证据要求。自动合并必须满足验收项、相关回归检查与独立审查；降低或删除要求需用户确认，人工检查项等待用户处理。
- 首版保留每节点工具调用、产物、审查反馈、token、费用和耗时，界面默认摘要、按需展开。费用按配置价格计算并标明估算，供应商实际账单可用时核对；未知价格显示未知，不按零处理。
- 汇合默认等待所有必需分支成功；失败分支重试或返工，成功结果保留。仅预先标记为可选的分支允许缺席，不能临时降低要求以继续执行。
- 对抗式验证要求反驳附证据，存在未解决且影响验收的有效反例则不通过，不以多数票压过反例。多视角验证要求所有必需维度通过，建议项不阻塞。评委式先检查硬性要求，再按预定标准评分；全部不合格则返工，胜者吸收其他方案后重新验证。
- 子图是可展开容器，内部仍只有 Agent 节点与程序节点，不额外代表 Agent；全图及子图共享 10 个运行名额，内部 Agent 身份与额度独立。子图向外输出结果、产物与证据。
- Q49 修正：执行中提出新增功能，属于新的功能任务，按首版单任务规则排队；原任务继续原验收范围，不将新增功能并入原任务后让旧结果失效。
- Graph 首版采用真实任务和执行机制两组验收，具体清单见设计汇总。
